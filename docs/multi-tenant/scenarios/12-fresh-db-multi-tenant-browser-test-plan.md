## 1. 背景与目标

### 1.1 为什么需要新库

现有联调库（`itsm_prod`）经过多轮 MSP 验收与浏览器演练，已积累历史租户、探针用户、历史工单与审计数据。这些数据会干扰"从零开通"的判定（例如：编码复用、首管冲突、列表噪声、序列/配额状态），也不利于把"部署 → 建租户 → 建用户 → 业务闭环"作为一条**可重现的完整证据链**留档。

因此本计划要求：**准备一个全新的数据库**，从迁移/播种开始，把整套多租户场景从 0 跑通，所有业务动作在浏览器中以真实用户视角完成，并保留可复核的证据。

### 1.2 目标（做什么）

| # | 目标 | 说明 |
|---|---|---|
| 1 | 全新库 + `saas_msp` 部署验证 | 新库初始化（迁移/播种）→ 启动后端/前端 → 健康检查与模式自检全绿 |
| 2 | 租户模型正确 | 平台创建 1 个 `msp_provider` + 2 个 `msp_customer`，客户绑定唯一服务商 |
| 3 | 三类建号通道可用 | 平台通道（超管跨租户建号）、租户通道（管理员在本租户建号）、MSP 通道（服务商为客户建号） |
| 4 | 业务操作可完成 | 普通用户浏览器登录并完成工单类型创建、工单创建等日常业务 |
| 5 | 权限/角色正确 | 超级管理员 / 服务商管理员 / 服务商员工 / 客户管理员 / 普通用户的菜单、路由、接口三层一致 |
| 6 | 跨租户协作闭环 | 客户建单 → 服务商工作台处理（回复/状态/指派）→ 客户回看 → 客户确认解决，单据状态与权限全程正确 |
| 7 | 隔离与审计可证 | 未分配客户、跨租户头冲突、客户访问 MSP 面等负向场景全部被拒且留痕 |

### 1.3 非目标（不做什么）

- 不做性能/容量/压测（并发、批量规模另立计划）；
- 不修改生产环境（`itsm_prod`）与既有联调数据；
- 不以修复代码缺陷为目标：执行中发现的问题**记录并登记**，是否修复由研发排期决定；
- 不以 API 脚本替代浏览器操作：接口/数据库命令仅作为**独立复核**手段（判定以浏览器可见行为 + Network 证据为准）。

### 1.4 执行形态

- **主通道（必做）**：人工按《操作手册》在浏览器（Chrome/Edge）中逐步操作；每阶段保留关键界面截图与 Network 证据。
- **自动化复跑（可选）**：用 Playwright（`itsm-frontend/tests/e2e/flows/flow-msp-workbench-ui.spec.ts` 等）或浏览器自动化工具在**同一环境**复跑关键链路，作为回归证据。
- **交叉验证（可选）**：`scripts/msp/acceptance/run-msp-business-acceptance.ps1` 等 API 验收脚本用于交叉核对（不能替代浏览器步骤）。
- **阶段 0 例外**：部署与数据库初始化属运维动作（非浏览器）；从阶段 1 起全部为浏览器操作。

### 2.1 阶段 0 · 部署环境（`saas_msp` + 全新库）

**丰富后的目标**

1. 在**独立的新库**上完成 schema 迁移与基础播种（不得复用/污染 `itsm_prod`）；
2. 后端以 `DEPLOYMENT_MODE=saas_msp` 启动，启动日志出现门控与自检信息；
3. 前端可访问并可登录；`/api/v1/healthz`、`/api/v1/readyz` 返回 200；`/api/v1/msp/status` 返回 `deploymentMode=saas_msp`、`mspRoutesEnabled=true`；
4. 记录环境指纹：库名/端口、应用版本（commit）、迁移账本状态、启动时间，作为后续证据的基线。

**验收判据**

- [ ] 新库初始化完成（迁移无失败项，播种后平台 `admin` 可登录）；
- [ ] `tenant_guard: pass`（启动日志）；`deployment self-check` 无 mismatch（`saas_msp` 初期无 provider 租户属预期告警，创建 provider 后复检消除）；
- [ ] `/msp/status` 与配置一致；未登录访问受保护接口返回 401（而非 200）；
- [ ] 环境指纹已记录（含新库名与批次号）。

**反例（顺带验证）**

- `DEPLOYMENT_MODE` 空值/未知值 → 启动失败（显式拒绝）；
- 非 `saas_msp`（如 `private`）→ `/api/v1/msp/*` 整族 404（复核后必须重启回 `saas_msp`）。

### 2.2 阶段 1 · 平台创建租户（1 provider + 2 customer）

**丰富后的目标**

1. 平台管理员（`super_admin`）在 `/admin/tenants` 创建 **1 个 `msp_provider`**（服务商）与 **2 个 `msp_customer`**（客户 A / 客户 B），两个客户均绑定同一服务商；
2. 每个租户完成**开通向导**（模板供给 → 首个管理员 → 完成），首管首次登录强制改密；
3. 服务商管理员登录后，客户目录/分配下拉中可见客户 A/B。

**验收判据**

- [ ] 租户列表三行齐备，类型分别为 `MSP服务商`、`MSP客户`×2；状态 `活跃`；
- [ ] 客户详情/接口中 `mspProviderId` = 服务商租户 id；服务商侧 `/msp/customers` 可见两个客户；
- [ ] 三个租户 readiness 就绪（模板 7 项基线计数 > 0），首管可登录且强制改密生效；
- [ ] 首管账号命名符合策略（`admin-<租户编码规整>`，可自定义）。

**反例（顺带验证）**

- 编码重复 → 保存被拒；编码非法（空格/特殊字符）→ 表单校验拒绝；
- 客户类型不选服务商 → 必填校验拒绝；服务商下拉为空（无 provider 时）→ 先建 provider。

### 2.3 阶段 2 · 超级管理员在目标租户建用户

**丰富后的目标**

1. 平台管理员通过 `/admin/tenants` 行内「建号」在**目标租户内**创建用户（跨租户建号通道）：
   - provider 租户：创建服务商管理员/员工，**必须选择 MSP 角色**（`provider_admin` / `provider_agent`）；
   - 客户租户（可选）：创建客户方管理员/普通用户（用于对照，客户管理员自建见阶段 3）；
2. 验证建号后账号归属、角色与可登录性；
3. 记录建号通道开关状态（默认开启；显式关闭时跨租户建号 404/业务错误）。

**验收判据**

- [ ] 新账号出现在目标租户用户列表，`tenant_id`/home 归属正确；
- [ ] provider 员工登录后具备 MSP 面（工作台等菜单可见），且 `msp_role` 正确；
- [ ] 客户租户用户登录后进入客户业务页（无 MSP 菜单）；
- [ ] 不勾选角色时按默认角色（最终用户 `end_user`）建号且可登录（对照口径）。

**反例（顺带验证）**

- 用户名重复 → 明确报错不产生脏数据；
- provider 租户建号不带 MSP 角色 → 登录后 MSP 面不可达（记录为预期约束）；
- 非平台账号访问平台建号入口 → 无入口/403。

### 2.4 阶段 3 · 租户管理员登录后创建普通用户

**丰富后的目标**

1. **服务商管理员**在自己租户内创建普通用户（租户通道 `/admin/users`，按现状能力执行；如当前版本要求走平台通道/带 MSP 角色，则以实际界面为准并在手册中标注）；
2. **服务商管理员**通过 MSP 通道（`/msp/management` →「为客户建号」）为客户 A 创建一个普通用户（跨租户授权写通道，服务端二次校验分配）；
3. **客户 A 管理员**、**客户 B 管理员**分别在 `/admin/users` 创建本租户普通用户；
4. 验证新用户登录落正确租户、具备基础业务权限（能建单）。

**验收判据**

- [ ] 三个新普通用户均可登录，`tenantId` 与 home 租户一致；
- [ ] 客户 A/B 用户互相看不到对方数据（后续阶段 5 负向复核）；
- [ ] 未分配该客户的服务商员工调用「为客户建号」被拒（403/业务错误，界面内联报错）。

### 2.5 阶段 4 · 普通用户登录与业务操作

**丰富后的目标**

1. 客户 A 普通用户登录 → 建立**工单类型**（或「从预设安装」）→ 新建工单（主线单据）；
2. 客户 B 普通用户登录 → 建立样本工单（用于隔离对照）；
3. 验证工单编号生成、列表/详情字段一致、状态初始值正确；
4. 可选扩展：服务请求/事件等其它单据各建 1 条样本，用于阶段 6/7 的跨租户读面验证。

**验收判据**

- [ ] 类型列表出现新建类型；建单页可选择该类型；
- [ ] 工单提交成功并生成编号（`TKT-<年月>-<序号>`）；列表与详情可查；
- [ ] 标题/描述/优先级/类型与提交一致；客户 B 的工单在客户 A 视图中不可见。

**反例（顺带验证）**

- 标题过短/描述过短 → 前端校验拒绝；
- 未建类型直接建单 → 类型选择器为空（记录为已知限制，不判失败）；
- 客户 A 用户直访客户 B 工单 URL → 404/403 且不泄露标题。

### 2.6 阶段 5 · 权限/角色正确性验证

**丰富后的目标**

以**三层一致**的方式验证五类角色的权限边界（详见 §3 矩阵）：

| 层 | 验证手法 | 证据 |
|---|---|---|
| L1 菜单/入口 | 各角色登录后观察侧栏/顶栏菜单项 | 截图（角色 × 菜单） |
| L2 路由直访 | 在地址栏直访无权限页面（如客户访问 `/admin/tenants`、`/msp/workbench`） | 页面 403/重定向截图 |
| L3 接口 | DevTools Network 观察关键请求的响应码与 `reasonCode` | Network 截图/导出（含 403/401 与错误码） |

**必须覆盖的负向场景**（与场景 08 的 N1–N6 矩阵同源；执行清单见《操作手册》§5.3）：

- 客户账号访问 MSP 面（页面与 `/api/v1/msp/*`）→ 403「仅MSP员工可访问」；
- 客户账号访问平台面（`/admin/tenants`、`/api/v1/tenants`）→ 403「仅平台管理员可执行该操作」；
- 未分配客户的服务商员工访问该客户数据（头通道 / 路径通道 / 请求体 / 深度切换）→ 403 + `MSP_ALLOCATION_REQUIRED`（客户不存在 404 `CUSTOMER_TENANT_NOT_FOUND`；客户停用 `CUSTOMER_INACTIVE`）；
- 跨租户头与登录租户冲突（`X-Tenant-Code`）→ 401 + `TENANT_MISMATCH_REJECTED`，且审计留痕（`tenant.probe_denied`）；
- 平台管理员进入 MSP 工作台 → 403（平台面与 MSP 面隔离；MSP 面要求 provider 身份 + `msp_role`）；
- 未授权租户切换 → 403 + 审计 `tenant.switch_denied`；
- 平台治理写通道关闭时（如 `TENANT_USER_ADMIN_ENABLED=false`）→ 403 + `TENANT_USER_ADMIN_DISABLED`；非 `super_admin` 调平台治理 → 403 `PLATFORM_SCOPE_REQUIRED`（如开启则记录开关状态）。

**验收判据**

- [ ] 五类角色的菜单/路由/接口期望全部匹配（允许/拒绝均与矩阵一致）；
- [ ] 所有负向场景均为"预期拒绝"，且**无静默放行**（冲突头不得被忽略后返回 200）；
- [ ] 拒绝事件可在审计看板/审计接口中检索到；
- [ ] 完成分配后同一请求由 403 变 200（授权即时生效，无需重启）。

### 2.7 阶段 6 · 跨租户协作与单据闭环

**丰富后的目标**

1. **可见性**：服务商员工登录 → `/msp/workbench`（跨客户工作台）可见客户 A 的工单；客户 B 未分配时不可见；
2. **处理**：对客户 A 工单执行行内操作——回复（客户可见）→ 改状态（如 `处理中`）→ 指派（当前技术员）；
3. **客户回看**：客户 A 用户刷新工单详情，可见服务商回复与状态变化；
4. **闭环**：**客户管理员**提交解决方案/确认解决（`resolve`，受保护终局）→ 状态到 `resolved`，服务商侧可见终态；普通用户（`end_user`）词表上具备 `ticket:update`（本人单据可按生命周期守卫解决），本计划以**客户管理员路径**为主口径，普通用户路径作为可选复核；
5. **深度切换（对照路径）**：服务商员工从客户过滤器「进入客户」做单客户深度操作，验证"当前客户（深度操作中）"指示与「返回工作台」恢复；
6. **审计**：工作台动作与拒绝事件均可在 `/msp/audit`（或审计接口）检索。

**验收判据**

- [ ] 工作台列表含客户列，且仅显示有效分配客户的单据；
- [ ] 回复内容在客户侧可见；状态变更双向一致；
- [ ] 指派后处理人正确（当前 MSP 技术员）；
- [ ] 客户管理员确认解决成功且终态正确（记录实际端点：受保护 `resolve` vs 编辑改状态，差异作为发现登记）；服务商侧后续操作按状态机收敛；
- [ ] 服务商侧不将 `resolved/closed` 作为工作台改状态步骤（服务商无 resolve 端点；下拉中若出现该选项，点击失败属已知契约不一致，记录不判失败）；
- [ ] 每个动作产生条目级审计（`workbench.action` 类事件）；
- [ ] 批量操作（如执行）：先展示客户分布确认，逐条结果可查（成功/失败分列）。

**反例（顺带验证）**

- 未分配客户在头/路径/请求体/切换四通道访问 → 403（同阶段 5）；
- 客户被暂停（如执行）→ 条目只读（`CUSTOMER_INACTIVE`）；
- 批量混合不可操作条目 → 逐条失败原因可见，成功条目不受影响。

### 2.9 补充性需求（贯穿全程）

| 项 | 要求 |
|---|---|
| 可重现 | 每阶段步骤、输入、预期、证据四要素齐全；重跑换新批次编码（如 `MSPT2/CUSTA2/CUSTB2`），不清理旧批次 |

## 3. 角色、账号与权限矩阵

### 3.1 角色定义（本计划使用的五类主角色）

| 角色 | 身份口径 | Home 租户 | 核心能力面 | 关键约束 |
|---|---|---|---|---|
| 平台超级管理员 | `super_admin`（平台根租户） | `default` | 租户治理、跨租户建号、平台审计、用户治理（写通道开关） | 平台面与业务面隔离；不进入 MSP 工作台 |
| 服务商管理员 | provider 首管：`users.role=admin` + `users.msp_role=provider_admin` + membership 组合角色 `provider_tenant_admin`（= `admin` ∪ `msp_admin`；membership.msp_role=`msp_admin`） | provider 租户 | 分配管理、为客户建号、工作台全动作、审计看板 | 数据面按分配收敛；跨客户操作需 allocation；MSP 面 RBAC 按 `provider_admin→msp_manager` 映射 |
| 服务商员工 | `msp_role=provider_agent`（RBAC 映射 `msp_tech`） | provider 租户 | 工作台查看/处理（回复/改状态/指派/批量，按分配与条目授权）；分配管理只读 | 无 `msp_customer:write`（不能为客户建号）；未分配客户不可见、不可写（403）；无 MSP 侧 resolve 端点 |
| 客户管理员 | 客户首管：`role=admin` + 客户侧角色边 | 客户租户 | 本租户建号/邀请、类型与工单管理、确认解决（`ticket:update`） | 无 MSP/平台入口；跨租户不可见 |
| 客户普通用户 | `end_user`（默认角色；权限含 `ticket:read/write/create/update`） | 客户租户 | 建单、查看/维护**本人**单据（改状态/解决按生命周期守卫：创建人/受理人/管理员）、评论 | 无 `ticket:assign`（不能指派）；仅本租户数据；无管理入口 |

> 角色/权限解析以 membership → `role_permissions` 为准（fail-closed）；MSP 面另有身份门（`msp_role`）与 RBAC 角色映射；客户租户内不得授予 MSP/平台专属角色（授予校验会拒绝）。权限词表对 `ticket:write` 做同义补齐（⇒ `create/update`），持有 write 的角色在路由细分动作下不会 403。执行前用目标版本复核一次（见 §3.4）。

## 5. 环境与部署计划（新库）

### 5.1 拓扑目标

```text
浏览器（Chrome/Edge）
   └─ 前端（Vite dev，:3000 或独立端口）
        └─ /api 代理 ──> 后端（saas_msp，:8090 或独立端口）
                            ├─ PostgreSQL：★ 全新数据库（独立于 itsm_prod）
                            └─ Redis：独立 DB index / 独立实例
```

### 5.2 新库方案对比（执行前决策）

| 方案 | 形态 | 隔离度 | 成本 | 适用 |
|---|---|---|---|---|
| A（推荐默认） | 复用现有 PostgreSQL 实例，**新建独立数据库**（如 `itsm_msp_fdb`）；后端独立端口/进程指向新库 | 高（数据完全独立；实例共享） | 低（无需新容器） | 现有隧道/实例可用、只需隔离数据 |
| B | 全新 Docker Compose 项目（独立 PG/Redis/MinIO 卷 + 独立端口） | 最高（含依赖完全隔离） | 中（拉镜像/起栈） | Docker Desktop 可用且允许拉镜像；需要"整套环境"独立 |
| C（不推荐） | 直接复用 `itsm_prod` | 低 | 最低 | 仅快速冒烟；会污染既有数据与判定 |

**决策规则**：

1. 默认按方案 A 执行；若执行环境允许且需要更强隔离，升级为方案 B；
2. **禁止**在未备份的情况下对现有库执行 `db-reset` 类破坏性操作；
3. 无论 A/B，新库必须有独立库名与批次标识，并在证据中记录库名与连接端口（不记录口令）。
4. 注意：仓库根 `Makefile` **没有** `db-reset` target（旧文档命令不可用）；`cmd/migrate -fresh/-reset/-down` 会 DROP/回滚数据库，禁止对 `itsm_prod` 使用，测试库也仅谨慎使用；
5. 方案 A 的新库与 `itsm_prod` 同实例：建议 `REDIS_DB=1`（或独立 Redis）隔离键空间；库创建/初始化命令见《操作手册》§0（含无本地 `psql` 时的远程容器执行方式）；
6. `readyz` 要求初始化组件（当前 **7 个**）全部 succeeded 且迁移账本最新——阶段 0 校验以此为准（部分文档仍写"六个组件"，属文档漂移）。

### 5.3 部署校验清单（阶段 0 出口）

| # | 校验项 | 方法 | 通过标准 |
|---|---|---|---|
| 1 | 服务就绪 | `GET /api/v1/healthz`、`/api/v1/readyz` | 200（`readyz` 503 = 组件/迁移未就绪，回查初始化日志） |
| 2 | 模式正确 | `GET /api/v1/msp/status`（登录态） | `deploymentMode=saas_msp`、`mspRoutesEnabled=true` |
| 3 | 启动自检 | 后端启动日志 | 门控解析 + `tenant_guard: pass`；创建 provider 后 self-check 无 mismatch |
| 4 | 平台账号 | 浏览器 `/login` | 平台管理员可登录并见「租户管理」 |
| 5 | 迁移账本 | 新库迁移状态 | 无失败项；与目标版本一致 |

> 具体命令（新库创建、迁移/播种、后端/前端启动）见《操作手册》§0；命令以目标版本仓库脚本为准。

## 6. 执行方式与证据规范

### 6.1 执行顺序

1. 阶段 0（运维，非浏览器）→ 2. 阶段 1–4（浏览器主线）→ 3. 阶段 5（权限矩阵 + 负向）→ 4. 阶段 6（跨租户闭环）→ 5. 阶段 7（选做）→ 6. 归档与复盘。

每个阶段结束先做该阶段判据自查，再进入下一阶段；阻断性问题挂起并登记。

### 6.2 证据规范

| 证据 | 要求 | 命名/位置 |
|---|---|---|
| 界面截图 | 每个阶段关键步骤 ≥1 张；含操作结果与页面状态 | `docs/multi-tenant/evidence/fresh-db-browser-<批次>/stage<N>/<seq>-<desc>.png` |
| Network 证据 | 负向场景与关键写操作：含请求方法/路径、状态码、`reasonCode` | 同上目录，`<seq>-<desc>-network.png` 或 HAR 导出 |
| 运行摘要 | 每阶段 PASS/FAIL/SKIP + 证据指针 | 同目录 `run-summary-<ts>.md`（可参考既有 acceptance 脚本产物格式） |
| 数据抽查 | 可选：租户/成员/分配/工单关键字段 | 摘要中附 SQL 与结果（只读） |
| 环境指纹 | 库名、端口、commit、批次、时间窗 | `run-summary` 头部 |

### 6.3 判定规则

- **PASS**：界面反馈与预期一致 + 独立验证通过（至少一个第二证据）；
- **FAIL**：预期允许被拒 / 预期拒绝被放行 / 数据错误 / 状态机被绕过；必须记录"请求 + 实际 + 期望"；
- **SKIP**：仅限前置缺失或开关未开，必须写明原因，且不得影响主线闭环；
- **出口**：阶段 0–6 主线无 FAIL；负向场景全部按预期拒绝；证据归档完整。

|---|---|---|

| 场景 00–11 | 逐步界面剧本与判据来源 | 本计划的详细步骤底稿 |

| 1 | 隧道/数据库/Redis 不可用；远程主机（方案 A）不可达或磁盘不足 | 后端无法启动、隧道与新库创建失败 | 阶段 0 前置检查（含 `Test-NetConnection 172.18.3.238 -Port 22` 与远程 `df -h /`）；不可达改用方案 B（本地 Docker）或恢复网络；磁盘低于 500M 先清理/扩容 |
| 2 | Docker Desktop 未运行（如走方案 B） | 无法起容器/迁移 | 先启动 Docker；或用方案 A（复用现有实例） |
| 3 | 无本地 `psql` 客户端 | 新库创建/抽查不便 | 用容器内 `psql`（`docker exec`）或远程主机命令；操作手册给出替代 |
| 4 | 建号通道开关状态 | 跨租户建号 404/403 | 执行前确认 `USER_PROVISIONING_CHANNELS_ENABLED`（默认开启）并记录 |
| 5 | 模板 7 项基线不含工单类型 | 新客户租户建单类型为空 | 阶段 4 先建类型/从预设安装（已知限制，不判失败） |
| 6 | provider 员工建号必须带 MSP 角色 | 不带则 MSP 面不可达 | 阶段 2 建号时必选；如遗漏，重建或平台补角色 |
| 7 | 登录/接口限流 | 密集操作被 429/403 | 控制节奏；必要时调高 `LOGIN_RATE_LIMIT_PER_MIN` 并记录 |
| 8 | 平台治理写通道默认关 | 阶段 7 平台重置/启停不可用 | 如需执行，显式开启 `TENANT_USER_ADMIN_ENABLED` 并记录开关证据 |
| 9 | 浏览器自动化工具可用性 | 自动化复跑失败 | 以人工浏览器操作为主证据；自动化仅作可选 |
| 10 | 口令与敏感信息 | 泄露风险 | 口令不入文档/仓库；本地凭据清单；执行后轮换 |
| 11 | 客户确认解决的 UI 入口与受保护 `resolve` 不一致 | 可能经 `PUT /tickets/:id` 直改状态、绕过解决方案前置 | 执行时记录实际端点并作为发现登记；受保护口径用 `POST /tickets/:id/resolve`（接口复核）；不阻断闭环主线判定 |
| 12 | 工作台状态下拉可能含 `resolved/closed` | 服务商点击必然失败 | 服务商步骤只用 `处理中/等待中`；该现象作为契约不一致记录 |
| 13 | 租户通道建 provider 员工无 `msp_role` | 无法进入 MSP 工作台 | 工作台员工一律走平台通道（可选 MSP 角色）或邀请通道；租户通道仅验证通道本身 |
| 14 | 文档与代码口径漂移（`07:G4`/`07:G5`/`07:G6` 关闭状态、组件数 6 vs 7、`db-reset` 缺失等） | 按旧文档操作会失败/误判 | 以实测与代码为准；执行前复核操作手册命令；漂移登记到发现清单 |
| 15 | 宿主环境变量覆盖 `.env`（godotenv 不覆盖已有 env） | 改了 `.env` 仍连旧库/旧模式 | 启动会话显式设置 `DB_*`/`REDIS_*`/`DEPLOYMENT_MODE`（手册 §0 方式）；不依赖 `.env` 自动生效 |
