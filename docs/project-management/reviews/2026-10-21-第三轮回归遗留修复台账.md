## 2. B1 · 输入静默改写（第三轮唯一实质未修复项）→ 根因重做

### 为什么上一轮"改了却没生效"

上一轮在 `InputNumber` 上加了 `onChange` 判断 `value > 1000000` 就提示。**但这条路径永远不会触发**：

- antd `InputNumber` 在**失焦**时才把越界值钳制到 `max`；
- `onChange` 回调拿到的已是**钳制后**的值（`999999999` → `1000000`）；
- 因此 `value > max` 恒为 false，提示从未出现，用户只看到数值"自己变了"。

### 本次修复（三层）

| 层 | 变更 |
|---|---|
| **上限口径** | `MaxTaskHours`：`1e6` → **`10000`**（约 5.5 人年 @ 8h×250 天）。原 100 万小时对"人月级"项目毫无约束力 |
| **前端（写入侧）** | 任务弹窗改为 **Form.Item 校验器**：超限直接 `reject`，字段下方红字「估算工时上限为 10,000 小时，请调整后再保存」，**阻止提交**（不再静默截断）；`extra` 明示区间 |
| **后端（写入侧）** | `validateHours` 已对 `> MaxTaskHours` 返回 400（沿用）；模板任务工时同步收敛到同一上限（原为 100000，口径分裂） |
| **后端（汇总侧）** | `SumTaskHours` 跳过越界值，并在响应新增 `invalidHoursTasks` / `invalidEstimateHours` / `invalidActualHours` / `maxTaskHours` |
| **前端（展示侧）** | 概览工时汇总下方显式告警：「已排除 N 个越界工时任务（估算 Xh / 实际 Yh，上限 10000h/任务）；请修正后重新统计」 |

### 为什么还要"汇总侧护栏"

第三轮实测 DB 中已存在 `estimate_hours=1000000` 的历史行（项目 9 汇总 `1000009h`）。
写入侧修复**不能追溯**已落库的脏数据，所以汇总层必须排除并显式回报，否则错误数字会一直当作事实参与报表。

### 验证

- `TestTaskHoursUpperBoundRejects`：`999999999` → 400；`== MaxTaskHours` → 通过；更新路径同样拒绝。
- `TestHoursSummaryExcludesInvalid`：库中 9h + 1000000h → 汇总 **9h**（不是 1000009h）、`invalidHoursTasks=1`、`invalidEstimateHours=1000000`、`maxTaskHours=10000`。

## 4. 新增-2 · 阶段门「门禁阻塞项」列被压到 0 宽 → 本次修复

**根因**：该列原本只有 `width: 360` 而无 `minWidth`，在 `scroll.x` 与 `fixed:'right'` 操作列共同作用下被弹性压缩到 0。

**修复**：
- 列增 `minWidth: 260` + `onCell` 强制 `minWidth/whiteSpace`；
- 表格 `scroll.x` 1100 → **1360**，并加 `tableLayout="fixed"`（宽度按声明分配，不再挤压弹性列）。
