## 2. 逐条核验与处置

### A1 · 必填校验完全失效（P0）→ 本次修复

- **源码事实**：`CreateRequest` 仅 `name` 有 binding required；`Service.Create` 只校验名称/类型。
- **修复**：
  - 后端新增 `Service.SetStrictCreate(true)`（bootstrap 生产装配开启）：`managerId` / `departmentId` / `startDate+endDate` 缺失 → 400 `ErrRequiredProjectFields`；
  - 前端新建项目弹窗：项目经理、所属部门、计划起止三处加 `required` 规则（双保险）。
- **兼容**：测试、导入脚本、存量自动化可 `SetStrictCreate(false)` 保持旧行为；不引入迁移。
- **验证**：`TestStrictCreateRequiresOwnerAndPlan`。

### A2 · 所属部门不写入后端（P0）→ 源码已具备 + 展示补强

- **核验**：`ent/schema/project.go` 有 `department_id`；`Create/Update` 均写入（`SetNillableDepartmentID`）；
  PE-28 已加同租户/未软删校验（`ErrDepartmentUnavailable`）。报告中的现象来自更早的部署版本。
- **本次补强**（消除「归口 = -」的可读性问题）：
  - 响应新增 `departmentName` / `managerName`（批量富化，失败降级为空）；
  - 列表新增「所属部门」列（缺失显示 `未设置`，不再显示 `-`）；详情「概览」新增所属部门；
  - 组合视图行新增项目经理/所属部门列；
  - 状态报告正文新增「所属部门：<名称>」。
- **未做**：存量空部门数据不回填（需业务确认真实归口）。
- **验证**：`TestProjectDisplayNamesEnriched`。

### A3 · 结项清单首屏数据陈旧（P0）→ 本次修复

- **根因**：清单自动项（任务清零/单据终态/结项门）是**读时派生**，但前端只在首次进入页面时拉取一次；
  任务/里程碑变更后没有刷新，导致首屏展示旧判定。
- **修复**：
  - 进入「结项清单」Tab 即强制 `fetchClosure + fetchGates`；
  - 任务创建/编辑/流转/删除、里程碑创建/流转/删除后主动刷新清单与门预检；
  - 读取失败时清空清单并提示（不渲染旧的「已通过」）。
- **验证**：前端 `tsc` + ESLint；后端派生接口 `GetClosure` 单测（PE-15 全链路）保持通过。

### A4 · 阶段门审批策略不一致且不透明（P0）→ 本次修复

- **保留的既有设计**：无审批流程时降级自动放行（D-17），保证存量租户可用。
- **本次修复**（「可识别 + 可引导」，不改变降级行为）：
  - 后端 `ProjectGateResponse` 新增 `approvalMode`（manual|auto|pending）+ `autoApproved`；
  - 预检 `GateReadiness` 新增 `approvalMode` / `autoApprovalConfigMissing`（`GateApprovalPort` 可选实现 `GateApprovalModeInspector`）；
  - 前端阶段门 Tab：顶部提示「当前门未配置审批流程：提交将自动放行」，并对所有自动放行门给出 `Alert` +「配置审批流程 →」直达 `/admin/process-routing`；
  - 门行「提交 / 裁决」列显示审批方式标签。
- **验证**：`TestGateApprovalModeExposed`、`TestPreviewGatesApprovalMode`。

### A5 · 计划门「通过时冻结基线」未执行（P1）→ 源码语义确认 + 文案修正

- **核验**：`applyGatePassSideEffects` 在计划门通过时**无基线则冻结 v1；已有基线不重复冻结**（D4）。
  报告期待「自动产生 v2」，与设计 D4 不一致，属**文档/界面文案**问题而非缺陷。
- **修复**：前端门定义文案改为「无基线时自动冻结 v1，已有基线不重复」，消除预期落差。
- **回归**：`TestGateRulesAndSequence`（plan 通过 → 基线 v1）保持通过。

### A6 · 时间源整体偏移（P0）→ 本次修复（展示/编号层）

- **根因**：服务端/前端都用 UTC 直接截断字符串（`slice(0,10)` / `Format("20060102")`），在东八区跨天。
- **修复**：
  - 后端新增 `business_time.go`（默认 `Asia/Shanghai`，可用 `ITSM_BUSINESS_TIMEZONE` 覆盖，内嵌 tzdata）：
    项目编号日期、报告生成时间、报告内时间统一按业务时区格式化；存储仍 UTC（无需迁移）；
  - 前端新增 `formatBusinessDate/formatBusinessDateTime`，替换项目列表/详情/风险/模板/组合视图/报告面板中的字符串截断。
- **未做**：存量数据不回填；已生成的历史编号不重写（不可变标识）。
- **验证**：`TestProjectCodeUsesBusinessTimezone`；前端 `formatters` 单测。

### A7 · 健康度算法失效（P1）→ 源码已修 + 本次补数据完备度

- **核验**：PE-27 已把 `health` 改为读时派生（9 条规则 + `healthReasons[]`），并已通过列表/组合/报表同源验证。
- **本次补强**（报告「始终健康」的剩余成因：**事实不足**而非规则失灵）：
  - 派生结果新增 `DataQuality`/`DataGaps`；判定缺口：无项目经理、无所属部门、非规划中缺计划日期、无基线、无任务；
  - 响应 `healthDataQuality=insufficient` + `healthDataGaps[]`；报告 Markdown 输出「数据缺口」并标注「数据不足，结论仅供参考」；
  - 前端 `ProjectHealthTag` 对数据不足显示灰色「健康（数据不足）」，Popover 列出缺口。
- **兼容**：不改变既有 9 条规则的判级（避免历史报表口径跳变）。
- **验证**：`TestHealthDataQuality`、既有 `TestDeriveHealthRules` 全绿。

### A8 · 阻塞数口径矛盾、结项按钮未禁用（P0）→ 本次修复
