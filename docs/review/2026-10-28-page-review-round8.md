## 0. 结论摘要

本轮做两件事：**验收 plan.md 的 13 项修复是否真的落地**，以及**补测未覆盖路径**。

结论是 **「修了一半，且修的地方出现了新的同类问题」**：

- **确认生效 4 项**：P1-4（顶栏角色标签）、P2-3（主用户表角色中文化）、P2-7（下拉浮层可达性）、P2-6 部分（配置项/知识推荐空态）。
- **确认未生效 1 项**：**P1-3（BPMN 原始标识外露）在部署构建里仍然存在**，且问题范围比原报告**更大**——不只在「流转进度」卡片，**「审批链」页签整块 6 处文案全部是未翻译的 i18n key**。
- **新发现缺陷共 14 项：P1 × 4（N1/N4/N6/N14）、P2 × 10（N2/N3/N5/N7~N13）、P3 × 0**，其中多项属于「同一个修复只改了局部、漏了同族用法」：P2-3 修了主用户表但漏了服务方成员表（`msp_specialist` 未进词表）；P1-4 修了顶栏标签但侧边栏仍残留 `Super_admin`/`Admin` 原始代码。

**最该先修的四件事**：

1. **P1-3 复现（N6）**：`user_task` / `userTask` / `exclusiveGateway` 仍然直接给业务用户看——这是上一轮就列为 P1 的问题，修复未在部署构建生效。
2. **N4**：审批链页签 6 处 i18n key 裸渲染（`detailTabs.bpmnStatusRunning` 等），词表里根本没有这些键。
3. **N14**：P1-1 就绪度仍是 7 项，**没有"服务目录项 / 工单类型"**，新租户依然会"开通全绿但无目录"——上一轮的 P1 一号问题没有被消除。
4. **N1**：邀请链接域名是 `http://localhost:3000/invite/...`，被邀请人点开必然失败——这是"邀请用户"链路唯一的交付物，等于链路断在最后一步。

## 2. 新发现问题清单

### N1【P1】邀请链接域名硬编码为 `localhost:3000`，被邀请人无法打开

- **现象**：`/admin/users` → 邀请用户 → 创建 `review.user@example.com` 成功后，列表给出的一次性链接为
  `http://localhost:3000/invite/...`
- **证据**：邀请结果弹窗与列表"复制链接"给出的都是 `localhost:3000`，而当前访问域名是 `172.18.3.238:8089`。
- **用户影响**：**邀请链路的唯一交付物就是这个链接**。客户管理员把链接发给新同事，对方打不开；管理员也不会意识到要手工把 `localhost:3000` 换成真实域名。这不是"多一步"的问题，是**功能在这套部署下不可用**。
- **建议**：邀请链接基址改取运行时配置（如 `NEXT_PUBLIC_APP_BASE_URL` / 请求 `Host` 头），禁止回落到 `localhost:3000`；缺失配置时应在创建前报错而不是产出一个坏链接。

### N2【P2】用户列表「角色」列同一角色徽标重复渲染两次

- **现象**：角色列每行出现两个同色徽标，内容相同，如"安全管理员 安全管理员"、"最终用户 最终用户"、"制造-安全管理员 制造-安全管理员"。
- **用户影响**：用户第一反应是"这个人有两个角色"，但两个徽标文字完全一样，无法判断是重复数据还是渲染 bug。角色数量是权限面判断依据，重复徽标直接污染这个判断。
- **根因线索**：`PRIMARY_ROLE_LABEL[record.role]` 与 `record.roleNames` 两路都渲染，而 `roleNames` 里含与主角色同名项，未去重。
- **建议**：渲染前对"主角色标签 + 已映射 roleNames"做去重（按 label 或 code 唯一），单一角色只出一个徽标。

### N3【P2】服务方成员表「服务方角色」列仍裸透 `msp_specialist`

- **现象**：「服务方成员（只读）」表里，服务方角色列显示原始代码 `msp_tech`、`msp_specialist`；同页主用户表已是中文。
- **证据**：`src/lib/api/user-api.ts` 的 `ROLE_LABEL_MAP` 收录了 `msp_tech: '服务商技术员'`，**但没有 `msp_specialist`**——所以 `msp_specialist` 走到"未映射 code 返回 null/原样"分支被裸透。
- **用户影响**：P2-3 的修复目标是"未映射 code 不裸透"，这条同族路径漏改，客户管理员在同一页面看到中英混排。
- **建议**：补齐 `msp_specialist`（服务商专员/专项工程师）等全部 `msp_*` 枚举；并把服务方成员表接入同一映射函数，避免逐表补。

### N4【P1】工单详情「审批链」页签 6 处 i18n key 未翻译，整块外露

- **现象**：页签内直接显示
  `detailTabs.bpmnStatusRunning`、`detailTabs.viewProcessDiagram`、`detailTabs.bpmnCurrentNode`、
  `detailTabs.bpmnTypeUserTask`、`detailTabs.bpmnTypeExclusiveGateway`、`detailTabs.bpmnIsGateway`
- **证据（源码）**：`src/lib/i18n/translations.ts` 中上述 6 个键 **grep 计数均为 0（不存在）**；同批的 `requesterCannotApprove` / `requesterNoApproval` 计数为 2（存在）。说明不是构建问题，是**词表漏登记**。
- **用户影响**：审批链是"这张单谁在批、批到哪一步"的核心视图。整块变成 `detailTabs.bpmnTypeExclusiveGateway` 这样的字符串，等于该功能区对业务用户完全不可读。比上一轮 P1-3 的"个别原始 id"更严重——**功能区域整体失效**。
- **建议**：补齐这 6 个键的中文词条（运行中/查看流程图/当前节点/用户任务/网关/是否网关分支）；并在 CI 加一条"渲染前扫描 `t('...')` 字面量是否都在词表内"的门禁，防止同类再漏。

### N5【P2】`ticketDetail.formFields` 键名外露，且 `t() || 兜底` 写法本身失效

- **现象**：工单详情「动态表单」卡片标题显示 `ticketDetail.formFields`。
- **证据（源码）**：`TicketDetail.tsx:1116`
  `title={t('ticketDetail.formFields') || '动态表单字段'}`；
  而 `useI18n.ts:49` 明确 `return key; // 如果还是找不到，返回原始键`。
- **根因**：`t()` 缺键时返回**键名字符串**（truthy），`||` 右侧兜底永远不执行。这是一个**可复制的错误范式**，仓库里其他 `t(key) || '兜底'` 写法同样失效。
- **建议**：① 补 `ticketDetail.formFields` 词条；② 全仓排查 `t(...) ||` 模式，改为 `t(key)` 后判断 `result === key` 再兜底，或给 `t()` 增加 `defaultValue` 参数。

### N6【P1】流转进度仍外露 `user_task` / `userTask` / `exclusiveGateway`（P1-3 未生效）

- **现象**：工单 #63「流转进度」卡片：
  - 当前节点 `user_task`（附"任务分配"）
  - 下一步 `userTask`（附"工单处理"）、`exclusiveGateway`（附"是否需要审批?"）、"网关分支"
  - 进度 `0/3`
- **对照**：`plan.md` P1-3 声称已在前端 `WorkflowProgressCard` 与后端 enrich 阶段改为业务显示名 + 中文类型标签。
- **判断**：部署构建 `37f5d9fe` 的实测表现与原报告一致，**该项修复未产生用户可见效果**。可能原因：节点本身未配 `name` 属性、后端 enrich 未覆盖该查询路径、或中文类型映射未命中 `user_task`（下划线写法）分支。
- **建议**：按 `plan.md` P1-3 逐条复验——先确认接口返回里 `currentActivityName` 是否仍为空，再确认 `BpmnActivityType` 映射表是否同时覆盖 `userTask`/`user_task` 两种写法。当前证据显示**两种写法都没被映射**。

### N7【P2】同一页面两种互斥文案并存

- **现象**：工单 #63 详情页同时出现
  - 顶部："**您是此工单的申请人，无法进行审批操作**"（`hasPendingApproval === true` 分支）
  - 审批链页签："**该工单未走审批流程**"
- **矛盾点**：既然"未走审批流程"，就不该有"无法进行审批操作"的提示；反之亦然。
- **根因线索**：`hasPendingApproval` 来自 `TicketApprovalApi.getApprovalRecords({status:'pending'})`，而审批链页签走另一路 BPMN 状态取数。**两个数据源对"是否有审批"给出不同答案**，前端各自渲染，导致同页自相矛盾。
- **用户影响**：这正是上一轮 P2-5 想消除的误解，换个形式又出现了——用户会去找"谁能批这张单"。
- **建议**：以单一数据源判定"是否有待办审批/是否走审批流"，两处共用同一结果；`0/3` 进度与"未走审批流程"也应统一口径。

### N8【P2】服务目录顶部统计与下方标签页计数不一致

- **现象**：服务目录页（同屏可见）
  - 顶部卡片：服务总数 `3`、云资源服务 `0`、**账号与权限 `2`**、安全服务 `0`
  - 下方标签页：全部服务 `(3)`、终端支持 `(1)`、网络与访问 `(1)`、**账号与权限 `(1)`**
- **硬矛盾**：同一个"账号与权限"分类，上方说 2、下方说 1；且上方三个分类合计 `0+2+0=2`，与服务总数 3 不符；下方 `1+1+1=3` 才自洽。
- **用户影响**：客户管理员靠顶部卡片判断"我有哪些服务可用"，数字错了会直接导致他去找不存在的第 2 个账号类服务；也让人怀疑整个服务目录的数据可信度。
- **建议**：顶部卡片与标签页计数走同一聚合口径（按服务项 `category` 精确计数，而非按名称模糊匹配/含子串匹配）；补一条"分类计数之和 == 服务总数"的断言测试。

### N9【P2】工单详情「SLA 定义」为空，仅剩一个冒号

- **现象**：工单 #63 详情右侧「SLA信息」区块：`SLA定义 :`（冒号后无任何值、无占位说明）
- **对照**：P2-6 的修复覆盖了"受影响配置项""知识推荐"，**漏了 SLA 定义**。
- **用户影响**：上一轮已指出"SLA 空白尤其敏感——客户会怀疑这张单到底有没有 SLA 保障"。现在只剩一个孤零零的冒号，比空白更像"渲染出错"。
- **建议**：SLA 未命中时显式输出"该租户尚未配置 SLA 定义，请联系管理员"；不要输出无值的 `SLA定义 :`。

### N10【P2】角色原始代码在侧边栏普遍残留，与顶栏中文标签不一致

- **现象**：
  - 客户管理员登录：顶栏"陈志远（制造-管理员）/ **管理员**"，侧边栏底部"制造-管理员 / **Admin**"；
  - 平台管理员登录：顶栏"系统管理员 / **超级管理员**"（中文），侧边栏底部"系统管理员 / **Super_admin**"（原始代码）。
- **用户影响**：P1-4 只改了顶栏一处，侧边栏同位置仍外露 code，且**两种角色都复现**，说明这不是个别映射缺失而是"侧边栏未接入统一词表"。同一身份在相邻两处一中一英，观感上明确是"改了一半"。
- **建议**：侧边栏与顶栏共用同一 `ROLE_LABEL_MAP` 取值，不在组件内各自判断。

### N11【P2】租户列表 `default` 租户域名字段显示 `localhost`

- **现象**：`/admin/tenants` 中 `MSP Provider Tenant default • **localhost**`，其余租户域名位为空。
- **同源判断**：与 N1 同一根因——站点基址回落到了 `localhost`，只是这次体现在租户域名字段。
- **用户影响**：平台管理员会认为该租户"域名是 localhost"，与真实访问地址（`172.18.3.238:8089`）不符，也解释了为什么邀请链接会拼出 `localhost:3000`。
- **建议**：与 N1 一并处理——统一从运行时配置取站点基址，禁止 `localhost` 回落。

### N12【P2】租户表格列宽严重不足，表头与单元格逐字竖排

- **现象**：表头渲染为竖排两行"资源（换行）使用"、"配（换行）额"、"到期（换行）时间"；单元格里"3"与"用（换行）户"、`1 本月 工单`、"不（换行）限"同样被压成竖排。
- **用户影响**：租户列表是平台运营主视图，"资源使用"这一列正是本轮刚修好的 P1-2 数据（3 用户/6 用户），却因为列宽不够变成竖排碎字，**修好的数据看不出来**。
- **建议**：给"资源使用"设定最小宽度并禁止 `word-break` 逐字换行（`white-space: nowrap` + 合理 `min-width`），或把"用户数/工单数"拆成两个窄列。

### N13【P2】租户列表"配额""到期时间"两列全为占位值，却占据首屏宽度

- **现象**：6 条记录的"配额"全部为"不限"、"到期时间"全部为"无"。
- **用户影响**：两列零信息量，却在列宽已经不够的情况下继续挤占"资源使用"的空间（与 N12 叠加）。平台管理员看不到任何配额/到期信息，也得不到"这两列当前不可用"的提示。
- **建议**：数据未配置时收敛为行内次要标记或折叠进详情，把宽度让给"资源使用"；或明确展示"未设置"并提供入口。与 P3-3（演示数据）一并处理。

### N14【P1】P1-1 就绪度未增补"服务目录项/工单类型"，新租户仍会"全绿但无目录"

- **现象**：以平台管理员打开 `review-test`「开通」向导，第 1 步"模板供给"就绪度仍**只有 7 项**：
  角色 30、权限 165、角色权限绑定 1042、菜单 89、审批组 6、SLA 定义 7、CI 类型 8 —— 全部标记"已就绪"。
- **对照**：`plan.md` P1-1 第 2 条要求"在 `tenantReadinessChecks()` 增补 `service_catalog_items`、`ticket_types` 两项"。
- **判断**：**该项未生效**。7 项全绿 → 向导会给出"开通完成"的结论，但服务目录与工单类型不在检查范围内，**新客户仍然会走到"开通全绿却无服务可申请"的老坑**，且系统不会提示。
- **用户影响**：这是上一轮排第一的 P1 问题（新客户接入卡在第一步），本轮验收显示其**核心症状未被消除**——只是"开通模板"侧可能补了引子数据，但就绪度语义仍未把"业务数据是否可走"纳入判断。
- **建议**：按 `plan.md` P1-1 补齐两项非必需提示项（区分"基线就绪 / 业务数据待配置"）；验收标准是**向导里能看到这两项**，而不是只看服务目录有没有数据。

### 3.2 每角色的断言清单（可复用的验收脚本口径）

1. `/admin/users`：主「角色」列 → 全部中文、**无重复徽标**、无裸 code；
2. 「服务方成员（只读）」表 → 服务方角色全中文（当前 ❌ `msp_specialist`）；
3. 邀请用户：创建 → 列表状态"待接受" → **链接域名 == 当前访问域名**（当前 ❌ localhost）；
4. `/service-catalog`：顶部四个计数之和 == 服务总数；顶部与标签页同名分类计数一致（当前 ❌）；

**B. 服务商经理（下一轮必测）**

1. 顶栏角色标签 == "服务商经理"（验 P1-4 在 provider 侧是否同样生效）；
2. `/msp/workbench`：**首屏不横向滚动即可看到 SLA 截止**（验 P2-2）；超期是否行级高亮；
3. 行内改状态 → **详情抽屉状态同步变化**（验 P2-1），且提示文案为中文目标状态；
4. `/msp/management`：说明文案无 `X-Customer-Tenant-ID`（验 P3-1）；
5. `/msp/audit`：事件分布全中文（验 P3-2）；越权明细可定位到人/租户/原因码。

**C. 平台运维（下一轮必测）**

1. `/admin/tenants`：**新租户"资源使用"用户数 == 实际建号数**（验 P1-2，本轮未测）；
2. 新建 MSP 客户租户 → 开通向导：就绪度是否含"服务目录项/工单类型"两项（验 P1-1）；
3. 开通模板后 → 首管登录 → **服务目录非空**（验 P1-1 核心断言）；
4. 服务目录空态（若可构造）→ 是否有"去创建"引导。

**D. 终端用户（下一轮必测）**

1. `/tickets/create`：顶部提示与描述校验是否一致（验 P2-4）；
2. 打开自己刚建、无审批环节的工单 → 是否仍出现"无法进行审批操作"（验 P2-5/N7）；
3. 侧边栏/顶栏是否**不出现** MSP 工作台与客户筛选器（角色隔离断言）。

### 3.3 每轮都应包含的三类断言

1. **术语断言**：页面文本中不得出现 `[a-z]+_[a-z]+`、`camelCase`、`xxx.yyyZzz` 形态的标识（自动扫描可做）；
2. **数据自洽断言**：汇总数 == 明细数之和；同一指标在不同视图同一屏内必须一致；
3. **同页不矛盾断言**：同一对象的状态结论，页面各处不得互斥。
