# 多租户功能实测审查报告（用户视角）

**Status: historical** — 带日期的历史快照，只证明 2026-10-28 当次运行。

> **审查日期**：2026-10-28
> **审查环境**：演示栈 `itsm-demo`，入口 `http://172.18.3.238:8089`（部署模式 `saas_msp`）
> **审查方式**：真实浏览器点击操作（非接口脚本），模拟平台管理员、客户管理员、服务商经理三类真实用户
> **参照文档**：`docs/multi-tenant/05-usage-guide.md`（典型流程 A/B/C/D）、`07-known-gaps.md`、`demo-environment.md`
> **审查账号**：平台 `admin / Demo@2026!Admin`；服务商 `demo.msp.manager / Demo@2026!`；新建租户首管 `admin-review-test`

## 0. 结论摘要

**整体可用性：可用，核心链路全通。** 从"建租户 → 模板开通 → 建首管 → 建普通用户 → 用户首登改密 → 建工单 → 服务商跨租户协同"这条主链路，**8 个环节全部实测通过，无一处阻塞性失败、无一次报错中断**。模板开通的一次性供给能力和跨租户行内操作是本产品最亮眼的两块能力，实测表现稳定（30 角色/165 权限/1042 角色权限/89 菜单一次写入成功，7 项就绪度全绿）。

但**"能跑通"与"用得顺手"之间有明显落差**。共记录 **13 个问题**，其中：

| 等级 | 数量 | 用户可感知的影响 |
|---|---|---|
| **P0（阻塞）** | 0 | 无 |
| **P1（严重）** | 4 | 会让新客户开箱即用时"卡在第一步"、或看到明显不该给终端用户看的内部标识 |
| **P2（中等）** | 6 | 造成困惑、需要多试一次、或需要横向滚动才能看完数据 |
| **P3（轻微）** | 3 | 文案、术语、演示数据观感问题 |

**最需要修的三件事**：
1. **新租户开箱无服务目录**（P1-1）——模板开通"全绿"却装不出服务目录，客户想走"服务请求"直接卡死；
2. **租户列表用户数恒为 0**（P1-2）——平台管理员无法从列表判断客户是否已建号，规模化运营直接失效；
3. **工单流转进度暴露 BPMN 原始标识**（P1-3）——`user_task`、`exclusiveGateway` 直接给车间主管看。

### 1.2 做得好的地方（建议保留并作为卖点）

- **首管用户名自动派生**：填完租户编码，第 2 步用户名已预填 `admin-{code}`，减少一次输入和一次命名冲突——这是很到位的细节。
- **就绪度语义可视**：黄色"缺失/待供给"→ 绿色"已就绪"的状态切换，配合一次性供给量回显（30/165/1042…），让"模板开通到底装了什么"有了可核对的数字，比单纯一个"成功"toast 强得多。
- **强制改密不可绕过**：首登改密是硬阻断，且弱密码策略真实生效（实测 `abc` 被拒），安全基线没有走过场。
- **跨租户操作粒度克制**：工作台只对 MSP 托管单开启"回复/改状态/指派"，非托管单三个按钮是 disabled 而非隐藏，用户能看到"这里本可以操作但不是我的单"，语义比直接消失更友好。
- **审计看板可直接当治理工具用**：越权尝试明细带状态码（401）和原因码（`TENANT_MISMATCH_REJECTED`），出问题能直接定位到人、租户、通道。

## 2. 问题清单（按影响排序）

### P1-1 ｜ 新租户"模板开通全绿"但服务目录为空，客户走不通服务请求

- **现象**：新建租户完成"开通模板"后，7 项就绪度全部"已就绪"、提示"模板供给完成"，但进入**服务目录页面显示 0 个服务**。此时客户若想走"服务请求"流程，没有任何可选目录项。
- **复现**：`/admin/tenants` → 新建 MSP 客户租户 → 开通向导 → 开通模板 → 首管登录 → 服务目录 = 空。
- **根因线索**：就绪度 7 项为 roles / permissions / role permissions / menus / groups / SLA 定义 / CI 类型，**不包含服务目录与工单类型**；而 `demo-environment.md` 中的"服务目录：每租户 3 个 [DEMO] 目录项"来自种子脚本（`seed_demo_dataset.py`），并非租户模板产出。也就是说：**演示环境"开箱可用"的观感，是靠种子脚本补出来的，不是靠产品自身的开通能力。**
- **用户影响**：这是"新客户接入"最典型的第八步落地场景。客户管理员按向导走完全绿，会默认"系统配好了"，然后在服务请求处卡住，且**没有任何提示告诉他需要手工建目录**。
- **建议**：① 就绪度增补"服务目录项 ≥1"与"工单类型 ≥1"两项，或明确区分"基线就绪"与"业务数据待配置"；② 模板开通至少落一个通用目录项作引子；③ 服务目录空态给出"还没有服务项，去创建"的引导按钮，而不是纯空白。

### P1-2 ｜ 租户列表"资源使用"用户数恒为 0，与实际严重不一致

- **现象**：租户列表中新租户"审查测试科技"的"资源使用"列显示 **0 用户**，但点开"用户"弹窗显示"共 2 个用户"（首管 + review.agent）；后续创建第 3 个用户后弹窗变"共 3 位用户"，列表**仍为 0**。多次刷新列表不变。
- **对照**：MSP 工作台"客户用量"卡片显示成员 9 / 8 / 8，与真实用户数量级吻合——说明**统计能力本身是有的，问题出在租户列表这个视图的取数口径上**（疑似读的是配额表计数器而非 users 实际计数，或新租户计数未回写）。
- **用户影响**：平台管理员做客户运营时，第一眼就是列表。用户数为 0 会直接导致误判"这个客户还没建号 / 是死租户"，规模上去后无法靠列表做巡检，只能逐个点进去数。
- **建议**：列表用户数改为实时 `count(users where tenant_id=?)`，或明确标注"配额已用 / 配额上限"并在建号后刷新计数。

### P1-3 ｜ 工单详情"流转进度"直接暴露 BPMN 原始标识

- **现象**：普通客户管理员打开自己新建的工单，详情"流转进度"区块显示：
  - 节点名 `user_task`、`userTask`
  - 网关 `exclusiveGateway`
  - 分支条件原文 `是否需要审批?`
- **用户影响**：这些是流程建模层的技术标识，不是业务语言。车间主管、生产部经理看到 `exclusiveGateway` 完全无法理解"我的单现在在哪一步、该谁处理"。这直接损害了"流程可视化"这个功能存在的意义。
- **建议**：流程节点在发布时强制要求填写"业务显示名"，前端只渲染显示名；缺失显示名时降级为"处理中（第 N 步）"而不是回落到原始 id。

### P1-4 ｜ 服务商经理账号在顶栏被显示为 "End_user"

- **现象**：以 `demo.msp.manager`（provider_admin）登录，右上角用户区显示"林致远（服务商经理）"，但其下方角色标签是 **"End_user"**。
- **用户影响**：服务商经理是跨租户操作的**权限最高、风险最大**的角色。顶栏把他的角色标成最普通的"终端用户"，既是错误的权限暗示（会让他怀疑自己权限没生效），也是审计与截图留证时的严重误导——出事故复盘时，截图显示"End_user 做了跨租户操作"。
- **建议**：核对顶栏角色标签的取数（疑似取了首个角色或默认角色而非有效角色），复用 `07-known-gaps.md` G3 中"有效角色解析"的同一套逻辑。

### P2-1 ｜ 跨租户改状态后，详情弹窗不刷新，仍显示旧状态原始值

- **现象**：工作台行内"改状态"选"处理中"，提示"状态已更新"；但同一弹窗内工单详情状态仍显示 `new`（且是未翻译的原始枚举值）。关闭弹窗后列表已正确显示"处理中"。
- **判断**：**写入成功，纯前端状态同步缺陷**。但用户看到的是"我改了，页面说成功了，可它还显示没改"——会本能地再点一次，产生重复操作。
- **建议**：改状态成功后局部刷新详情，或直接提示"已更新为处理中"并关闭弹窗。

### P2-2 ｜ 工作台表格关键列被截断，需横向滚动

- **现象**：`/msp/workbench` 表格列依次为客户、工单号、标题、状态、优先级、负责人、SLA 截止、更新时间、操作。实测在常规宽度下**状态之后（优先级/负责人/SLA截止）被裁掉**，需拖动底部横向滚动条才能看到。
- **用户影响**：跨客户工作台的核心价值就是"一屏扫完哪个客户的单快超期、谁在处理"。而 SLA 截止恰好是最该被看见的列，却被推到视口外。同一页面"客户用量"卡片里显示"成员 9 / 未关闭 13 / 新增 26"，反倒是次要信息占了首屏。
- **建议**：把 SLA 截止、状态前置；或提供列配置/紧凑模式；至少让 SLA 超期以行级红色标记（现在超期信息埋在"2026/10/17 09:33:31 超期"整串文本里，不醒目）。

### P2-3 ｜ 用户管理角色列同时出现中文标签与未翻译代码

- **现象**：用户列表角色列同时渲染"**系统管理员**"中文徽标和"**customer_user**"原始代码徽标，二者并存。
- **用户影响**：同一个用户被标了两个角色样式，客户管理员无法判断"这个账号到底有几个角色、customer_user 是什么权限"。
- **建议**：统一走角色名映射表，未映射的代码不应直接透出；多角色用统一数量的徽标呈现。

### P2-4 ｜ 新建工单提示与校验自相矛盾

- **现象**：新建工单页顶部提示"**填写最少信息即可提交**"，但仅填标题、描述留空时，提交被"描述最少 10 个字符"拦截。
- **用户影响**："最少信息"到底含不含描述？用户按提示理解必然踩坑一次。这是典型的**文案与规则打架**，成本极低但感知极差。
- **建议**：要么改文案为"标题 + 描述即可提交"，要么描述允许为空并走默认值。

### P2-5 ｜ 新建工单为空时，弹窗内出现与当前场景无关的审批提示

- **现象**：申请人本人打开自己刚建的工单（无任何审批环节），页面出现"**您是此工单的申请人，无法进行审批操作**"。
- **用户影响**：这句话暗示"本单有审批、但你没资格批"，凭空制造了误解——用户会去找"谁能审批"。实际该工单根本没有审批任务。
- **建议**：无待办审批任务时不渲染该行提示，或改为"本单当前无审批环节"。

### P2-6 ｜ 新租户工单详情多处空区块无兜底文案

- **现象**：新租户工单详情的"SLA 定义"为空、"受影响配置项"为空、知识推荐为空，均为纯空白区域，无占位说明。
- **用户影响**：用户无法区分"这里本来就没有"与"这里加载失败了"。SLA 为空白尤其敏感——客户会怀疑"我这张单到底有没有 SLA 保障"。
- **建议**：空态统一给"未配置 SLA / 未关联配置项"等明确说明，SLA 未命中时提示"该租户尚未配置 SLA 定义，请联系管理员"。

### P2-7 ｜ 下拉选项在滚动容器内不可用节点点击（自动化/无障碍可达性缺陷）

- **现象**：创建租户时的"MSP 服务商"下拉、建号时的"角色"下拉，展开后其选项报"元素离屏"（`ElementOffscreen`），无法通过常规控件定位点击，只能按坐标点击才成功。
- **说明**：本次以真实鼠标坐标点击可正常选中，**人工使用不受影响**；但该现象通常意味着下拉浮层渲染在滚动容器外或被 `overflow` 裁剪，**对键盘 Tab 导航与读屏软件一般同样不友好**。
- **建议**：下拉浮层挂到 `body`/portal 层，并补充 `role="listbox"/"option"` 与键盘上下键支持。

### P3-1 ｜ 分配管理页说明文案暴露技术实现

- **现象**："使用说明"写的是"MSP 员工即可通过 **X-Customer-Tenant-ID 头**访问对应客户的工单"。
- **建议**：面向管理员的说明改为"分配后即可在工作台中查看并处理该客户的工单"；HTTP 头说明移到开发者文档。

### P3-2 ｜ 审计看板分布项混用中文与英文枚举

- **现象**："按事件分布"中同时出现中文"登录/工作台操作/租户冲突/探测"与英文 `view` / `search` / `pat` / `update` / `create` / `delete` / `export` / `upload`。
- **建议**：统一中文，技术枚举放 tooltip。

### P3-3 ｜ 演示数据 SLA 几乎 100% 超期，影响演示说服力

- **现象**：工作台"未关闭 39 / 超期 39 / 未指派"——**未关闭的全部超期**；按客户看超期 13/15/11 亦合计 39。
- **影响**：这不是功能缺陷，但让"我们 SLA 管理很专业"的演示变成"你们全是超期的"。演示环境应按 7:2:1 铺正常/临近/超期样本。
- **建议**：种子脚本调整 SLA 截止时间分布，保留少量临近与超期样本作演示，其余落在正常区间。

## 3. 用户视角的"顺手度"评估

| 维度 | 评分（5 分制） | 依据 |
|---|---|---|
| 主链路上手难度 | 4 | 向导三步线性推进，首管用户名自动预填，几乎不用思考 |
| 反馈明确度 | 3.5 | 模板开通有量化回显；但改状态后详情不刷新、空态无说明，反馈有断点 |
| 出错后的可恢复性 | 4 | 弱密码有明确提示、可原地重试；无死循环、无白屏、无需要刷新页面才能继续的卡点 |
| 术语可理解性 | 2.5 | 流转进度 `exclusiveGateway`、角色 `customer_user`、说明里的 `X-Customer-Tenant-ID`——三处把内部实现暴露给业务用户 |
| 数据可信度 | 2.5 | 租户列表 0 用户 vs 实际 3 用户，是"看到的数不能信"这类最难容忍的问题 |
| 视觉信息密度 | 3 | 工作台关键列被截断，需要横向滚动才能看到 SLA 截止 |

**一句话总结**：**流程设计是顺的，落地细节是糙的。** 该有的步骤一步不少、该有的校验一个不虚，但"每一步之后用户看到的反馈"和"界面上的每一个字是否是人话"这两块欠打磨。

## 4. 修复优先级建议

**立即修（下次发版前）**
1. P1-2 租户列表用户数统计口径 —— 一行 SQL 级别的修复，却是平台运营的第一眼数据。

7. P2-2 工作台列顺序与超期高亮、P2-6 空态文案、P3-1/P3-2 术语统一、P3-3 演示数据分布。
