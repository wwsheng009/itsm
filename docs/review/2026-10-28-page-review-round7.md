## 二、本轮五条最高优先级结论

### 结论 1（P0）｜三个页面出现"指标分母是模板占位符"，Bot 运行看板全页失效

Bot 运行看板是本轮**最严重的渲染缺陷**：时间筛选直接显示字符串 `最近 {7} 天`，八处指标的分母位置显示 `{0}`。这不是"数据为 0"，而是**模板变量根本没有被替换**。用户看到的是程序内部字符串，而非界面文案。

- `最近 {7} 天` —— `{7}` 是本应被数字 7 替换的占位符
- 八处 `{0}` 分母 —— 本应是实际的样本总数

危害等级高于"显示 0"：显示 0 至少语义完整，显示 `{0}` 说明**模板渲染管道断裂**，该页所有衍生指标（成功率、命中率等）在分母位置都没有真实值，整页数据不可用。

### 结论 2（P0）｜四处"指标自证"失败，其中两处是同页内硬矛盾

前六轮反复验证"总数 = 各分项之和"，本轮在两个页面出现同页矛盾：

| 页面 | 总数 | 分项 | 差额 |
|---|---|---|---|
| **已知错误** | 总数 **2** | 活动中 0 + 已解决 0 + 已废弃 0 = **0** | **2 ≠ 0** |
| **服务目录** | 服务总数 **3** | 云资源 0 + 账号与权限 2 + 安全服务 0 = **2** | **3 ≠ 2** |

已知错误页的两条记录**状态列全空**，这解释了 0 的来源——记录存在但状态字段没有值，所以三个状态桶都数不到它。总数 2 是对的，分项统计错了，根因是状态字段为空。

服务目录的问题不同：它连分类口径都不一致（见结论 3）。

### 结论 3（P0）｜服务目录存在"两套并行的服务分类体系"

同一个页面上，指标卡用的是 **云资源服务 / 账号与权限 / 安全服务**，页签用的是 **全部服务 / 终端支持 / 网络与访问 / 账号与权限**。两套名字只有"账号与权限"重叠。

- 指标卡分类合计 = 0+2+0 = 2
- 页签分类合计 = 1+1+1 = 3
- 顶部"服务总数"= 3

即：**页签口径自洽（1+1+1=3），指标卡口径不自洽（0+2+0=2≠3）**。同一页面两套分类体系并存，用户无法判断"云资源服务""安全服务"归到哪个页签下。

### 结论 4（P0）｜SLA 监控同页两处"未解决违规"数值相差 29

SLA 监控页顶部 KPI 区显示 **违规总数 29 / 未解决违规 29**；同一页面的概览页签内显示 **SLA 合规率 违规 0 (0.0%)** 与 **活跃告警 未解决违规 0 条**。

同一个术语"未解决违规"，在一屏之内既是 29 又是 0。这不可能是时延导致（同一次页面加载），只能是两个查询走了不同的统计口径或不同的数据源。**运维值班人员如果按 0 判断，会漏掉 29 条真实违规。**

### 结论 5（P0）｜新建资产的"采购价格"数值上限被设成 0，无法录入任何金额

新建资产表单中，"采购价格"是数值输入框，其 `valuemax = 0`。这意味着**用户无法输入任何正数价格**——填 1 会被拒绝，填 0 等于没填。

这不是校验过严，而是**控件约束配置错误**（上限写成了 0）。资产管理的关键字段被彻底封印，属功能性阻断。

## 三、逐页详录

### 第 1 页｜首页控制台（/dashboard）

- **P0｜运行时指标与前六轮结论直接冲突**。首页展示 系统运行时间 = **1 天 0 小时**、CPU = **35.5%**、内存 = **62.3%**，均为正常值。而第六轮系统配置页的同一批指标为 运行时间 = **未知**、Goroutine = **0**、CPU 核心数 = **0**、内存使用率 = **0%**。
  → 同一系统的运行时自检，一个页面显示"CPU 35.5%"，另一个页面显示"CPU 0 核"，**两者必有一错**。结合首页数值合理（正数、有时间跨度、百分比区间正常），可判定**系统配置页的运行时指标读取链路失效**，而非真实为 0。这条为第六轮的"运行时指标全 0"提供了决定性反证。
- **P2｜顶部通知徽标数字被拆成两个节点**。铃铛徽标渲染为 `46`，但在可访问性树中是两个独立文本节点 `"4"` 和 `"6"`。与第六轮通知中心"tab 徽标 46 拆成 4/6"同源，属**同一 children 拼接 bug 的第二处复现**。
- **P2｜侧边栏"自动化规则"仍出现两次**。第六轮已报告该问题，本轮复测 **uid=108 与 uid=126 仍为两个同名菜单项**，指向 `/workflow/automation` 与 `/admin/tickets/automation-rules` 两个不同功能。**未修复**。

### 第 2 页｜新建事件（/incidents/new）

三个页签：基本信息 / 影响分析 / 附件。

- **P1｜校验提示在用户尚未输入时就已出现（过早触发）**。"详细描述"字段下方在页面刚加载、用户未触碰任何控件时，即显示红色错误提示。用户会误以为"这个表单已经出错了"或"我填错了什么"。正确做法是 blur 后才校验，或提交时统一校验。
- **P1｜右侧"创建提示"侧栏不随页签切换，内容与当前页签无关**。切到"影响分析"页签时，右侧提示仍在讲"优先级"；切到"附件"页签时，提示还是讲"优先级"。三个页签共用一份静态提示，**上下文错配**，反而干扰操作。
- **P2｜「提 交」按钮文字中间被硬插空格**。可读名为 `提 交`（"提" + 空格 + "交"），与第六轮组管理页「刷 新」、权限页同类问题同源，属**图标与文字 flex 布局挤压所致**。
- **P2｜联系方式占位符以真实值样式展示**。表单中出现 `400-XXX-XXXX`，X 占位符未经弱化处理，视觉上像一个可用的号码。
- **P2｜「取 消」同样拆字**（"取" + 空格 + "消"）。
- **P2｜页签切换不写入 URL 与状态**。切到"影响分析"后刷新页面即丢失当前位置，无法分享/回退到指定页签。

### 第 3 页｜新建变更（/changes/new）

- **P1｜"详细描述"与"回滚计划"在未提交时即显示红色"请填写"**。与新建事件同病，且更严重——"回滚计划"是变更管理的高风险字段，未输入时立刻标红会让用户误判为已失败。
- **P2｜"变更理由"输入框的可访问名称混入了图标文字**。其 accessible name 里带 `question-circle`（帮助图标的内部名），屏幕阅读器会念出"变更理由 question-circle"。
- **P2｜「取 消」拆字**（第 2 次复现）。
- **P2｜与新建事件结构同构，但校验时机、按钮文案不一致**。两个同类新建表单未复用同一套表单基座，导致缺陷各自复现。

### 第 4 页｜新建发布（/releases/new）

- **P1｜"发布编号"必须人工输入且需遵守格式，无自动生成、无格式示例**。对比：工单编号由系统生成（`TKT-202610-000066`）、CI 编号需手填、资产编号需手填、发布编号需手填——**同一系统四种编号策略并存**，其中三种要求用户手工拼写格式。发布编号的 placeholder 未给出示例格式。
- **P2｜「取 消」拆字**（第 3 次）。
- **P2｜无"保存草稿"**。新建文章页有草稿能力，新建发布没有；发布属于多字段复杂表单，缺少暂存手段，用户中途离开即全部丢失。

### 第 5 页｜新建 CI（/cmdb/ci/new）

- **P1｜"扩展属性"要求用户手工填写 JSON，无语法校验、无示例、无模板**。CI 的扩展属性是 CMDB 的核心能力，但以裸文本框承接 JSON。用户写错一个逗号即可能静默失败或整条记录异常，且页面**没有 JSON 格式校验提示**。
- **P2｜25 个字段单页平铺，无分组、无折叠、无锚点**。字段多但信息架构平坦，用户难以定位（如"序列号"与"所属组织"混排）。
- **P2｜「取 消」拆字**（第 4 次）。
- **P2｜与新建资产、新建事件存在字段重叠但控件不统一**。"名称/描述/状态"在三个表单中的必填性、控件类型、顺序均不同。

### 第 6 页｜新建资产（/assets/new）

- **P0｜"采购价格"数值输入框 `valuemax = 0`，无法录入任何正数**。上限被配置为 0，用户即便填 1 也会被拒绝。资产管理最基础的金额字段完全不可用。**属控件约束配置错误，非校验策略问题。**
- **P1｜"资产编号"需人工按格式输入，无自动生成**（同第 4 页的编号策略问题）。
- **P2｜价格字段无货币单位选择**。只有数字，没有币种/单位（元/万元），跨币种场景无法表达。
- **P2｜「取 消」拆字**（第 5 次）。
- **P2｜必填项标识不统一**。部分字段带红色星号，部分必填字段无标识。

### 第 7 页｜新建文章（/knowledge/articles/new）

- **P1｜"分类"下拉的默认选中值直接显示内部 ID「1」**。用户打开页面就看到分类是"1"，而非分类名称（如"故障处理""操作指南"）。**内部主键泄漏到界面**，且默认值本身也不该被预选——用户可能误以为已选好分类。
- **P1｜只有"保存草稿"，没有"发布"动作**。知识库文章的核心闭环是"草稿 → 发布 → 可检索"，缺失发布入口意味着草稿可能永远无法进入知识库供检索。
- **P1｜说明文字"编辑器产出的富文本 HTML"重复出现两次**。同一条说明在同一区域渲染两遍，与第六轮"暂无数据 暂无数据"、用户管理"角色 角色"同源。
- **P2｜切换 Markdown / 纯文本格式后，说明文字不变**。格式已切换，但说明仍写着"编辑器产出的富文本 HTML"，与实际所选格式矛盾。
- **P2｜保存草稿后无可见的状态反馈说明**（草稿状态在列表页如何呈现未说明）。

### 第 8 页｜AI 创建工单（/ai/create-ticket）

- ✅ **优点｜"先分流、再建单，且明确不自动提交"的三段设计**。页面先以自助问答收集问题，再引导创建工单，并明确告知"只给建议，不会直接提交，写操作需人工审批"。这是本轮**AI 域最好的设计**——把 AI 的边界（建议 vs 执行）写在用户动手之前，而非事后免责。
- **P2｜"Pilot" 标记与页面成熟度不匹配**。该页已承载工单创建主流程，却标 Pilot，与稳定功能混排会让用户对可用性产生误判。
- **P2｜问答上下文不跨页面保留**。离开页面再回来，已收集的问题描述丢失。

### 第 9 页｜AI 评估与审计（/ai/evaluations）

- **P1｜表头列数与实际渲染列数不一致**。可访问性树中表头有 **8 列**（含"输入引用"），但页面实际渲染 **7 列**。"输入引用"列存在于 DOM 结构却未渲染，用户看不到 AI 决策所依据的输入内容——**这恰恰是审计页最该展示的证据**。
- **P2｜空表仍渲染完整表头与分页器**。
- **P2｜"Pilot" 标记**。审计类功能标 Pilot，会削弱其作为合规证据的可信度。

### 第 10 页｜AI 审批（/ai/approvals）

- **P1｜"计数"列宽不足，被逐字竖排**。表头渲染成"计"在上"数"在下两个字符，与第六轮权限页"选择角色："逐字竖排同源。列宽未设 min-width。
- **P1｜"确认时限"列被挤出容器右边界，内容被截断**。表格总宽超出容器，最右侧列不可完整阅读。
- **P2｜"暂无数据"重复渲染两次**（第 3 处同源复现）。
- **P2｜页面出现两个"刷新"按钮**。页头一个、表格工具栏一个，作用域与差异未区分。
- **P2｜0 条数据仍渲染表头与分页器**。

### 第 11 页｜Bot 运行看板（/ai/bots/dashboard）

- **P0｜时间筛选显示 `最近 {7} 天`，模板占位符未渲染**。`{7}` 是未替换的模板变量。用户看到的是程序内部字符串。
- **P0｜八处指标分母显示 `{0}`，模板占位符未渲染**。八处全是 `{0}`，说明模板渲染管道在下游整体断裂，不是个别字段问题。
- **P1｜分母为 0 时仍计算并渲染百分比**。即使占位符被替换成 0，`X/0` 也无数学定义，页面缺少除零保护。
- **P2｜Bot 能力开关与此页可用性矛盾（跨页）**。第六轮系统配置 AI 配置页中"Bot 能力"开关为**关闭**，但本页仍可正常访问并展示指标。
- **P2｜"Pilot" 标记**。

### 第 12 页｜NOC 工作台（/noc）

- **P1｜表格 6 列，"创建时间"列被挤出可视区，底部出现横向滚动条**。值班场景下最关键的时间信息默认不可见，需要横向拖动才能看到。
- **P2｜0 条数据仍渲染完整表头与分页器**。
- **P2｜空态与表格表头同时存在**。同屏既有"无数据"提示又有完整表头，语义重叠。
- **P2｜与第六轮部门管理同类的"空表占位"反模式**（未达 P0，因本页无错误态伪装）。

### 第 13 页｜SLA 监控（/sla/monitoring）

- **P0｜同页两处"未解决违规"数值相差 29**。KPI 区：违规总数 **29** / 未解决违规 **29**；概览页签：SLA 合规率 违规 **0（0.0%）** / 活跃告警 未解决违规 **0 条**。同一次加载、同一术语，29 与 0 并存。**按 0 值班会漏掉 29 条真实违规。**
- **P1｜"SLA 实时监控大屏"的统计周期文字被 KPI 卡遮挡**。标题与周期说明被上方指标卡覆盖，无法确认统计窗口是 24 小时还是 7 天——而统计周期直接决定违规数 29 的解读。
- **P2｜"合规率 违规 0（0.0%）"在分子分母同为 0 时仍输出百分比**。0/0 不应产出 0.0%，应为"无数据"。
- **P2｜空表仍占位**。

### 第 14 页｜待我审批-目录（/service-catalog/approvals）

- **P1｜"创建时间"直接输出原始 ISO 8601 UTC 时间戳**。显示为 `2026-10-28T02:10:02.779566Z`，含 T 分隔符、6 位微秒、Z 时区标记。这是**数据库原始值直出**，未经本地化。
  → 至此本系统存在**三种时间格式并存**：ISO 原始值（本页）、`2026/10/13 16:15:00`（用户管理）、`2026-10-28 09:43`（通知中心）。
- **P1｜"申请人"列显示主键而非姓名**。渲染为 `用户 #5`。审批场景下审批人必须看到"谁在申请"，显示主键等于没有信息。
- **P1｜表头"请求ID""申请人"被逐字竖排**。两列列宽不足，四字表头逐字换行成 4 行，与第 10 页"计数"竖排同源。
- **P2｜「批 准」「查 看」「拒 绝」三个按钮的文字中间均被硬插空格**。三个操作按钮全部拆字，与第 2 页「提 交」同源（第 6/7 处复现）。
- **P2｜审批操作无二次确认说明**。"拒绝"通常需填写理由，页面未提示。

### 第 15 页｜软件许可证（/assets/licenses）

- **P1｜"总许可证"卡片的图标渲染为「♂」符号**。应为许可证/文件类图标，实际渲染成男性符号，属**图标字体或字符编码错配**。
- **P2｜4 个指标卡与单独的"合规率"卡不成栅格**。前 4 张等宽并排，第 5 张单独换行且宽度不同，布局破裂。
- **P2｜表头 8 列超出可视宽度**，与第 12/16 页同类。
- **P2｜空表仍占位**。

### 第 16 页｜项目管理（/projects）

- **P1｜表头 8 列横向截断，仅可见 4 列**。"健康度""进度"等关键列被压出可视区。项目管理页看不到进度，功能实质残缺。
- **P2｜"共 1 个项目"文字对比度过低**，几乎与背景同色，难以辨认。
- **P2｜1 条数据仍渲染完整分页器**（上一页/下一页均禁用）。
- **P2｜1 个项目的数据量下，页面仍展示分页与"每页条数"下拉**，控件冗余。

### 第 17 页｜配置项列表（/cmdb/items，页面标题为"配置项工作台"）

- **P1｜侧边栏菜单名为"配置项列表"，页面标题为"配置项工作台"**。同一条目两个名字，与第六轮"组管理 / 用户组管理"同名不一致同源。
- **P1｜"类型"列直接输出英文枚举 code**。显示 `application` / `database` / `network`，未本地化为"应用系统/数据库/网络"。这是**根因 B（枚举 code 未本地化）的第 13 次复现**，也是跨轮次最顽固的问题。
- **P1｜描述承诺的筛选维度大于实际提供**。页面说明写"可按类型、状态、**关键程度**筛选"，但实际只提供 **2 个**筛选下拉（类型、状态），**"关键程度"筛选器不存在**。文档与实现不一致。
- **P2｜"云厂商""型号"两列所有行均为「-」**。字段存在但无数据，且"-"未区分"空值"与"不适用"。
- **P2｜「查 询」按钮拆字**（第 8 处复现）。

### 第 18 页｜拓扑图（/cmdb/topology）

- ✅ **优点｜"未选择配置项时刷新按钮正确禁用"**。这是全系统少见的**有理由的 disabled**——没有选中对象时刷新无意义，控件主动禁用而非放任点击报错。对比第六轮权限页"保存配置"无理由 disabled，此处是正确范例。
- ✅ **优点｜空态引导具体、可执行**。空态明确告知先选择配置项、再选择层级，而非只说"暂无数据"。
- **P2｜层级下拉默认值为「2 层」，但说明写支持 1–4 层**。默认值与可选范围说明未对齐，用户不确定 2 层是否为推荐值。

### 第 19 页｜已知错误（/problems/known-errors）

- **P0｜"总数 2"与三个状态分项合计 0，指标不自证**。顶部：总数 **2** / 活动中 **0** / 已解决 **0** / 已废弃 **0**。2 ≠ 0+0+0。**根因已定位**：表格中两条记录的"状态"列**全空**，因此三个状态桶都统计不到，而总数按行数计得 2。总数对、分项错，本质是状态字段缺失。
- **P1｜"状态"列两条记录全为空**。这是上条指标矛盾的直接原因，也使用户无法判断已知错误处于活动/已解决/已废弃。
- **P1｜"关键词"列两条记录全为空**。关键词是已知错误被检索命中的核心字段，为空则此功能无实际检索价值。
- **P1｜表头 9 列被横向截断，"分类"只剩「分」一个字符**。截图确认 "分类" 表头仅渲染出"分"，其后各列全部出界。
- **P2｜"操作"列 3 个按钮全部无 accessible name**（仅图标）。屏幕阅读器无法识别，用户不知可执行什么操作。
- **P2｜「重 置」按钮拆字**（第 9 处复现）。
- **P2｜"共 2 条"文字对比度过低**。

### 第 20 页｜服务目录（/service-catalog）

- **P0｜"服务总数 3"与分项合计 2 矛盾**。顶部：服务总数 **3** / 云资源服务 **0** / 账号与权限 **2** / 安全服务 **0**。0+2+0 = 2 ≠ 3。
- **P1｜指标卡与页签使用两套并行的服务分类体系**。
  - 指标卡：云资源服务 / 账号与权限 / 安全服务
  - 页签：全部服务 / 终端支持 / 网络与访问 / 账号与权限
  - 两套体系仅"账号与权限"重叠。页签口径自洽（1+1+1=3），指标卡口径不自洽（0+2+0=2）。用户无法确定"云资源服务""安全服务"属于哪个页签。
- **P1｜每张服务卡标题后固定渲染一个「—」**。三张卡的标题右侧均有破折号占位，说明某个应显示字段（如服务编号/版本）取值为空，用横线兜底，但未说明该位置本该是什么。
- **P1｜星级评分是 5 个独立 radio，全部 checked=false，不构成评分控件**。每张卡有 5 个独立 radio，accessible name 均为 `star star`（重复），且**全部未选中**。真正的星级评分应是单一 radiogroup 内 1–5 互斥选择，此处实现为 5 个无关联 radio，既不能评分也不能展示已有评分。
- **P2｜每张服务卡右下角有一个无 accessible name 的按钮**（仅图标）。三张卡共 3 个无名按钮，功能不可知。
- **P2｜"按申请热度推荐"但三张卡全部"0 次申请"**。热度排序的依据与结果矛盾：0 次申请无法产生热度排序。
- **P2｜「让 AI 帮我选」按钮文字对比度过低**。蓝底蓝字，文字几乎不可辨。
- **P2｜三个筛选下拉（分类筛选 / CI类型 / 云服务）均无选中值展示**。

## 四、系统性根因（跨轮次收敛）

本轮 20 个页面并非 20 个孤立缺陷，而是少数几个根因的重复爆发。按跨轮次出现次数排序：

### 根因 A｜模板变量/占位符未渲染 —— 本轮新增，危害最高
- 表现：`最近 {7} 天`、八处 `{0}` 分母、服务卡固定「—」、新建资产 `valuemax=0`
- 特征：**内部实现值直接出现在界面**（占位符、主键、枚举 code、原始时间戳）
- 危害：用户看到程序内部字符串，界面丧失语义
- 本轮出现：第 11 页（9 处）、第 20 页（3 处）、第 7 页（分类显示 ID「1」）、第 14 页（ISO 原始值）、第 14 页（用户 #5）

### 根因 B｜枚举 code 与内部值未本地化 —— 第 13 次复现
- 历史：R5 操作日志「操作人」空、R6 服务方角色 `msp_specialist`、R6 通知正文 `new→in_progress`、R6 组描述引用不存在的角色 slug
- 本轮：第 17 页类型列 `application`/`database`/`network`、第 7 页分类显示「1」、第 14 页申请人「用户 #5」
- **这是全系统最顽固的问题，跨 6 轮未修复**

### 根因 C｜表格列宽与容器宽度失配 —— 本轮高频
- 表现：列被挤出可视区（第 12/16/18 页）、表头逐字竖排（第 10 页"计数"、第 14 页"请求ID/申请人"）、内容被截断（第 10 页"确认时限"、第 19 页"分类"只剩"分"）
- 根因：列未设 min-width，表格总宽未做横向滚动或响应式收缩
- 本轮出现：7 个页面

### 根因 D｜错误态 / 空态 / 校验态三者不分 —— 承 R6
- 历史：R6 部门管理"加载失败"与"暂无部门"同屏
- 本轮：第 2/3 页"未输入即报错"（校验态过早）、第 10/19 页"空表仍渲染表头与分页"（空态未收敛）、第 13 页"0/0 仍算百分比"
- 本质：**状态机未定义**，各页面各自决定何时显示什么

### 根因 E｜指标口径未单点定义 —— 本轮新增
- 表现：第 19 页总数 2 vs 分项 0、第 20 页总数 3 vs 分项 2 且两套分类、第 13 页同页 29 vs 0
- 根因：**"总数"与"分项"由不同查询计算**，未共用同一数据源与过滤条件
- 这是前 6 轮"指标自证"方法在本轮失效的原因——前 6 轮多数页面自证通过，本轮四处失败

### 根因 F｜按钮文字被拆字 —— 第 9 处复现
- 历史：R6 组管理「刷 新」、权限页「选择角色：」竖排
- 本轮：`提 交`、`取 消`×5、`批 准`、`查 看`、`拒 绝`、`重 置`、`查 询`
- 根因：图标 + 文字 flex 布局在窄容器下将文字拆成两段

### 根因 G｜无障碍名称被污染 —— 承 R6
- 历史：R6 `collapsed 系统配置怎么用`（4 处）
- 本轮：第 3 页 `变更理由 question-circle`、第 20 页 `star star`（5 个 radio 同名）、多处操作按钮无名称
- 根因：图标 alt 文本与业务名称拼进同一 accessible name

## 七、本轮方法与局限（必须声明）

### 方法
- 每页均执行：页面结构快照（可访问性树）+ 视觉截图，两者交叉核对
- 表单类页面：读取控件约束（`valuemin`/`valuemax`/`required`/`disabled`/`checked`）、观察校验提示的**出现时机**、核对 placeholder 与说明文字
- 指标类页面：手工复算"总数 vs 分项之和"，差额直接记录
- 跨页核对：同一术语/同一指标在不同页面的取值

### 局限（不可忽略）
1. **未做任何真实提交**。用户约束为只读不改代码，而新建事件/变更/发布/CI/资产/文章一旦提交即写入真实业务数据。因此所有表单**只验证到字段与校验层，未验证提交后行为**（如：提交成功后跳转到哪、编号是否回填、草稿能否发布）。凡涉及提交后行为的结论，本文未做断言。
2. **"关系管理"页面未进入审查**。R5 清单列了 3 个 CMDB 页面，本轮完成配置项列表与拓扑图，**关系管理未测**（时间与上下文预算所限）。
3. **Bot 运行看板的 `{0}` 与 `{7}` 只观测到渲染结果**，未查阅模板源码，故未确定是后端未替换还是前端未插值。
4. **SLA 监控 29 vs 0 的两个数值均取自页面展示**，未核实底层数据，故只断言"两处不一致"，不断言"哪个对"。
5. **服务目录"两套分类"的判定基于页面展示**，未核实是否存在第三套后台分类表。
6. **软件许可证「♂」图标的成因未验证**，仅记录视觉结果（可能为图标字体缺失或字符映射错误）。
7. **未以非管理员账号复验**。所有页面均以 `admin` 身份访问，权限相关页面的可见性结论不适用于普通角色。
8. **未验证移动端/窄屏表现**。所有列宽问题基于当前视口宽度观测。
