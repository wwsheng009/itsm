## 0. 结论先行

前三轮的主要发现是「单页内部指标不自洽」。本轮把视角拉高一档，转向**跨页面口径比对**，结果比预期严重得多：**整个工作流 + SLA + 升级这条链路，每一环都给不出能与上一环咬合的数字。**

一句话概括本轮：

> 系统声称有 27 个流程实例在跑、25 个正在运行、24 条流程严重不健康、13 个工单超时；
> 但它同时声称工作流 18 个全是草稿、已启用 0 个、每个流程 0 个步骤、版本总数 0 个、升级规则 0 条、SLA 模板全未安装、SLA 定义适用服务全空。
> **一条零版本、零步骤、零规则、零适用服务的链路，无法产出 25 个正在运行的实例。**

这不是某一个字段写错了，而是**四层数据源各算各的**。用户在这个系统里做任何运营决策，都会得到互相矛盾的事实基础。

### 本轮三个最高优先级结论

| # | 结论 | 影响 |
|---|---|---|
| **A** | 工作流配置 / 版本管理 / 流程实例 三页互相否定 | 用户无法判断流程到底有没有部署、能不能改 |
| **B** | SLA 四页（定义 / 模板 / 配置 / 监控）对「SLA 是否生效」给出四种答案 | SLA 违规告警的可信度归零 |
| **C** | 升级规则 0 条，但 13 个超时工单存在 | 超时无人接管，是运营层面的真实漏损 |

## 1. 核心发现 A：工作流三页互相否定

### 实测数据对照

| 页面 | 关键指标 | 实测值 |
|---|---|---|
| 流程实例 `/workflow/instances` | 总实例 / 运行中 / 已完成 | **27 / 25 / 2** |
| 工作流配置 `/admin/workflows` | 工作流总数 / 已启用 / 活跃实例 / 平均步骤数 | **18 / 0 / 0 / 0** |
| 版本管理 `/workflow/versions` | 总版本数 / 激活版本 / 草稿 | **0 / 0 / 0** |
| 监控仪表盘 `/workflow/dashboard` | 运行实例 / 健康度 | **25** / 健康 1 · 严重 24 · 评分 4.0/100 |

### A-1【P1】18 个工作流全部「草稿」、已启用 0，但存在 27 个流程实例

- 工作流配置页 18 行「状态」列**无一例外全为「草稿」**，顶部「已启用 0」。
- 流程实例页明确列出 27 条实例，其中 25 条状态为「运行中」。
- **逻辑上不可能**：草稿状态的流程定义不应能启动实例。二者必有其一为错误数据，且页面未给出任何解释。

### A-2【P1】18 行「步骤: 0」，平均步骤数 0，但瓶颈分析页给出同一流程 5 个任务

- 工作流配置页每个流程名下均标注 `步骤: 0`，顶部「平均步骤数 0」。
- 节点瓶颈分析页对 `service_request_flow` 明确展示：最慢路径「任务数 **5**」、瓶颈任务「**审批任务**」。
- **同一流程，一处 0 步骤，一处 5 个任务**。BPMN 流程零步骤在语义上就不成立。

### A-3【P1】18 行「活跃实例 0 / 已完成 0 / 完成率 0%」全部为 0

- 与 A-1 同源：列表区实例统计全 0，与实例页 27 条直接冲突。
- 且 18 行的「最后修改」时间戳**完全相同**（`2026-10-13 08:14:54.104`），精确到毫秒，明显是种子批量写入而非真实编辑记录。

### A-4【P1】版本管理三项指标全 0，与 27 个实例矛盾；且选定流程 Key 后仍为空

- 「总版本数 0 / 激活版本 0 / 草稿 0」。
- 流程 Key 下拉实际提供三个 Key：`ticket_approval`、`incident_process`、`change_process`。手动输入 `ticket_approval` 回车后，页面仍显示「未找到版本数据」。
- 说明**空态是页面级的**（后端未返回任何版本数据），而非筛选条件所致。有流程在运行，却零个版本记录。

### A-5【P1】疑似重复流程 3 组，中文名与英文 key 同义并存

| 组 | 条目 1 | 条目 2 |
|---|---|---|
| 1 | `服务请求流程`（标准服务请求处理流程） | `service_request_flow_cn` |
| 2 | `问题管理流程`（问题管理全流程） | `problem_management_flow_cn` |
| 3 | `发布审批流程`（软件发布审批管理流程） | `release_approval_flow_cn` |

- 中英文同义流程并存，`_cn` 后缀版本无名称、无类型、无描述，用户**无法判断该启用哪一个**，也无法判断是否会造成重复分配。

### A-6【P1】「AI 工作流模板目录」表空态，但功能入口齐备

- 表格显示「暂无数据」，而页面同时提供「创建模板草稿」按钮、搜索框（key/名称/描述）、业务域下拉、状态下拉。
- 模板目录功能未落地，却已暴露完整交互外壳。

### A-7【P2】工作流配置页其他问题

- **「类型」列 18 行中约 12 行为空**：仅 工单分配流程/通用工单流程=工单流程、服务请求流程=服务请求、问题管理流程=问题管理，其余全空。
- **每行 4 个操作按钮中有 2 个是无文字、无 accessible name 的空按钮**（a11y 树中为裸 `button`），用户不知点击后果。
- **「版本」列显示裸数字徽章 `1`**，无 `v` 前缀，与「版本管理」页的版本概念无对应关系。
- **流程命名中英混排**：`工单分配流程` / `service_request_flow_cn` / `scheduled_inspection_flow` / `incident_emergency_flow_v1.1`，四种命名风格。
- **「全部类型」「全部状态」两个下拉无选中值展示**，仅有前置文字。

### A-8 ✅ 工作流配置页做对的地方

- 分页完整：共 18 条 / 10 条每页 / 页码 1-2 / 跳至 N 页，首页正确禁用「上一页」。
- 提供「工作流管理怎么用」折叠帮助入口。
- 首列复选框批量选择 + 「绑定规则」批量操作，批量能力在设计上是对的。
- 「工作流总数 18」与「共 18 条记录」一致。

## 2. 核心发现 B：SLA 四页给出四种「是否生效」答案

### 实测数据对照

| 页面 | 关键陈述 | 实测值 |
|---|---|---|
| SLA 模板 `/admin/sla-templates` | 模板安装状态 | 6 个模板 **全部「未安装」** |
| SLA 定义 `/admin/sla-definitions` | 定义启用状态 | 7 条定义 **全部「已启用」** |
| SLA 定义 | 适用服务 | 7 行 **全部为空** |
| SLA 配置 `/workflow/sla` | 告警引用的 SLA | 大量为 **`Default SLA`**（定义页无此条目） |

**四页合起来等于**：模板没装 → 定义却已启用 → 定义没绑任何服务 → 但告警已经在按一个不存在的 `Default SLA` 判违规。链条每一环都自相矛盾。

### B-1【P1】SLA 模板 6 个全「未安装」，但定义页 7 条全「已启用」

- 模板页自身文案承诺：「安装模板后系统会创建对应 SLA 定义」。
- 实际：0 个模板安装，却已有 7 条已启用定义。**模板与定义之间没有建立起可解释的因果**，用户无法判断「我现在到底有没有 SLA 在生效」。

### B-2【P1】7 条 SLA 定义「适用服务」列全部为空

- 7 条定义（Incident-P0/P1/P2/P3、ServiceRequest-标准、Change-普通、Change-紧急）均标记「已启用」，但**没有一条绑定适用服务**。
- 未绑定服务的 SLA 定义在逻辑上无从触发，与 SLA 配置页已产生的 29 条违规告警直接冲突。

### B-3【P1】「Default SLA」不在 SLA 定义清单中

- SLA 配置页 29 条告警的「SLA」列大量显示 `Default SLA`。
- SLA 定义页可查的 7 条名称中**不存在** `Default SLA`。
- 说明存在**未纳入管理界面的隐藏 SLA**，管理员既看不到也无法编辑，但它在持续产出告警。

### B-4【P1】SLA 定义页底部「服务商下发 只读」区块与主表三重冲突

- 主表：`Incident-P0-紧急`，ID `16`。
- 底部只读区另列两条：`Incident-P0-紧急 urgent 类型无关`、`Incident-P0-紧急 urgent 类型 #13`。
- 同一条 SLA 出现**三种不一致表述**（ID 16 / 类型无关 / #13），且「urgent 类型无关」这种字段拼接直接暴露给了用户。

### B-5【P1】SLA 模板页 6 个模板全「未安装」与 13 个超时工单并存

- 模板页是四页中唯一指标能自证的（6 模板 = 6 行、推荐 5、行业 3），但「全部未安装」的结论与系统已有 13 个超时工单的事实无法并存。

### B-6【P2】SLA 模板页其他问题

- 「服务类型」列显示英文枚举 `incident` / `change` / `service_request`；「优先级」列 `critical` / `high` / `medium` / `low`（根因 B 第 4 次）。
- 「模板」列一行内塞入模板名 + code + 推荐徽章 + 长描述，信息密度过高，列宽被挤压。

### B-7【P2】SLA 定义页其他问题

- 更新时间显示 ISO 原样 `2026-10-13T08:14:54.072365Z`，未本地化（同前几轮）。
- 操作列 4 个纯图标按钮，无文字、无 tooltip。
- 状态 / 优先级 / 类型三个筛选下拉均无选中值展示。
- ✅ **平均可用性 99.6% 与 7 行数值算术一致**（697.25 / 7 = 99.607），这是少数经得起验算的指标。
- ✅ 「服务指标」列用图标 + 文字双编码（响应/解决/可用性/7x24）。

## 3. 核心发现 C：SLA 配置页（/workflow/sla）—— 本轮问题最密集页面

页面面包屑为「首页 / 工作流 / SLA 配置」，侧边栏叫「SLA 配置」，而页面 H1 是「BPMN SLA监控」——**同一页面三个名字**。

### C-1【P1】日期筛选完全失效

- 日期范围设为 **2026-10-21 → 2026-10-28**。
- 但表格 29 条违规时间**全部落在 10-13 至 10-20**：`2026-10-13 16:19`、`2026-10-14 00:17`、`2026-10-16 22:56`、`2026-10-20 16:16`……无一在所选区间内。
- 筛选控件形同虚设，用户以为在看本周告警，实际看的是上周的。

### C-2【P1】严重级别与工单优先级倒挂

| 工单 | 优先级 | SLA 违规严重级别 |
|---|---|---|
| TKT-202610-000008 | Incident-**P0-紧急** | `low` |
| TKT-202610-000009 | Change-**紧急** | `low` |
| TKT-202610-000002 | Incident-P1-高 | `high` |
| TKT-202610-000003 | Incident-P2-中 | `high` |

- **最紧急的 P0 工单被判最低严重级别 `low`**，而 P2 中优先级反而是 `high`。告警优先级计算逻辑错误，会导致最该被处理的告警被排在最后。

### C-3【P1】响应超时与解决超时同刻双发，重复告警放大

- TKT-202610-000002 在 `16:19` 同时出现两条：`解决超时 high` + `响应超时 medium`。
- TKT-000003、TKT-000006、TKT-000007、TKT-000011、TKT-000012 均为同一时刻双条。
- 响应超时（起始阶段）在解决已超时（终局阶段）后不应再独立计一条，29 条告警中存在系统性重复计数。

### C-4【P1】「流程SLA指标」卡片零指标

- 卡片标题为「流程SLA指标」，内容只有「选择流程」下拉 + 起止日期两个筛选控件，**没有任何指标数值或图表**。名不副实。

### C-5【P1】「选择流程」未选却已展示全量告警

- 下拉显示占位文字「选择流程」（未选状态），告警列表仍输出全部 29 条。筛选语义不明：是"未选=全部"，还是"未选=不应显示"？

### C-6【P2】SLA 配置页其他问题

- 无分页控件，29 条一次性铺满，仅顶部「29 项」计数。
- 严重级别英文枚举 `low` / `high` / `medium`（根因 B 第 5 次）。
- 工单列 TKT 编号 + 标题**不可点击**，无法从告警下钻到工单详情。
- H1「BPMN SLA监控」被顶栏压住，截图中呈半透明重影（同 Round2 系统配置页、监控仪表盘，第 3 次出现）。

### C-7 ✅ SLA 配置页做对的地方

- **顶部 29 项 / 未处理 29 / 高严重级别 2 / 已处理 0，与表格 29 行、状态全未处理、`high` 恰好 2 条完全自证一致**——这是本轮唯一指标链完整闭合的页面。
- 违规类型用 badge 区分「解决超时」「响应超时」，状态用红色警示三角图标，视觉层级清晰。

## 4. 核心发现 D：监控仪表盘与瓶颈分析，两页给出相反结论

### D-1【P1】仪表盘与瓶颈分析对同一系统结论对立

| 页面 | 结论 |
|---|---|
| 监控仪表盘 | 流程健康度：健康 1 / 警告 0 / **严重 24**，评分 **4.0/100**（红） |
| 节点瓶颈分析 | `service_request_flow`：**LOW**、瓶颈任务数 **0** |

- 一个页面说"24 条流程严重不健康"，另一个页面说"这个流程没有瓶颈"。用户无从判断该信谁。

### D-2【P1】瓶颈分析判 LOW，但页面自身证据全部指向有瓶颈

同一页面同时给出三组自相矛盾的证据：
1. 系统优化建议：「考虑增加 **审批人员** 的容量」
2. 资源约束表：审批人员利用率 **85%**、容量 10、当前负载 8、约束 `capacity`
3. 最慢路径：任务数 5、瓶颈任务「**审批任务**」

既有瓶颈、又有优化建议、又有 85% 高利用率，却判「LOW / 瓶颈任务数 0」。

### D-3【P1】最慢路径「总耗时」显示裸纳秒值 `7200000000000`

- 未做任何单位换算。该值等于 7200 秒 = 2 小时，但用户只会看到一串 13 位数字。

### D-4【P1】仪表盘四组指标互相冲突

- **「热门流程」表显示「暂无流程实例数据」，但上方 KPI 明确「运行实例 25」**——有 25 个运行中实例，热门流程却一条都没有。
- **任务分布 created 25 (67.6%) + completed 12 (32.4%) = 37 条任务**，但「运行实例 25」、实例页「总实例 27」。三个数字互不相容；占比分母 37 与「总实例」口径不同却同页并列。
- **SLA 合规率空态写「所选时间范围内暂无已完成的流程实例」，但实例页明确有 2 条已完成**（10/17 09:44）。虽时间范围 10/21-10/28 可能排除 10/17，但页面未说明"因时间范围被排除"，用户会误认为系统没有已完成实例。
- **健康度显示 24 条「严重」，却没有任何下钻入口**告诉用户是哪 24 条、卡在哪个节点。

### D-5【P2】仪表盘 / 瓶颈分析其他问题

- 仪表盘「健康度评分 4.0/100」被拆成「4」+「.0」两个节点渲染（同 Round3 Bot 看板「0」+「.00」，数值拆分 bug 第 3 次）。
- 仪表盘任务分布状态列英文枚举 `created` / `completed`。
- 仪表盘 H1「BPMN流程监控仪表盘」被顶栏压住（同 Round2 系统配置页）。
- 仪表盘「今日完成 0」与「待处理任务 25」并列，用户无法判断 25 是今日新增还是历史积压。
- 瓶颈分析「瓶颈任务数 0」但「最慢路径」表内「瓶颈任务」列有值「审批任务」。
- 瓶颈分析「总等待时间 / 总处理时间」显示 `-`，却已有最慢路径总耗时数据。
- 瓶颈分析资源约束表英文枚举：类型 `human`、约束 `capacity`。
- 瓶颈分析双流程输入控件冗余：左侧下拉 + 右侧「或输入流程 key 检索」文本框显示同一值，且必须点「分析」才生效，易误解为已切换。
- 【P3】瓶颈分析「严重程度」显示为绿色 LOW + 三角图标，与同页优化建议色彩语义冲突。

### D-6 ✅ 仪表盘 / 瓶颈分析做对的地方

- 仪表盘日期范围选择器（起止 + 日历图标 + 清除）+ 刷新，默认近 7 天，口径明确。
- 仪表盘流程趋势折线图坐标轴完整（10/21-10/27 逐日 + 0-4 刻度）。
- 仪表盘 SLA 合规率空态写出了原因「所选时间范围内暂无已完成的流程实例，无法计算 SLA 合规率」——比单纯「暂无数据」好。
- 仪表盘健康度用三色语义（健康绿 / 警告黄 / 严重红）+ 评分双表达，一眼看出严重性。
- 瓶颈分析把指标定义写清楚了：「等待时间 = 节点创建到被领取；处理时间 = 领取到完成；总耗时 = 等待 + 处理」。
- 瓶颈分析资源约束表设计专业（类型 / 资源 / 利用率进度条 / 容量 / 当前负载 / 约束），85% 一眼看出接近上限。
- 瓶颈分析时间窗口提供 24小时 / 7天 / 30天 三档。

## 5. 核心发现 E：升级链路断裂

### E-1【P1】升级规则直连路由 404

- 访问 `/system/escalation-rules` 返回 **404**。
- 但侧边栏「升级规则」菜单可正常进入（实际走 `/admin` 前缀）。
- 后果：**深链不可分享，刷新即失效**。有 bookmarked 链接的用户会直接看到 404。

### E-2【P1】规则总数 0、总触发次数 0，但仪表盘有 13 个超时工单

- **13 个超时工单在零条升级规则下不可能被升级**，也就是说这些工单实际上无人接管。这是运营层面的真实漏损，不是显示问题。

### E-3【P1】升级矩阵：通知目标数 5 个，但表格只有 2 个目标 ID

### E-4【P1】升级矩阵：P1 L3 行目标类型 user，但目标 ID 显示「未指定」
