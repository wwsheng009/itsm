## 0. 结论摘要

第一轮已验证「多租户主链路能跑通」。第二轮换成**真实的客户管理员视角**逐页点过之后，结论变得更严格：

> **平台骨架完整、页面覆盖度足够，但「最后一公里」大面积失守。**
> 不是功能没做，而是**做出来的东西在关键节点上不给人用**：审批按钮在 DOM 里但视觉不渲染、AI 建单点了确认直接报错、通知正文是乱码、列表页把 18 条工作流显示成 0 条。

**共记录 46 个问题**：

| 等级 | 数量 | 用户可感知的影响 |
|---|---|---|
| **P0（完全阻塞）** | 0 | 无（系统整体可登录可用） |
| **P1（严重）** | 13 | 关键业务链路卡死、数据自相矛盾、技术标识直出给业务用户 |
| **P2（中等）** | 22 | 需多试一次、需横向滚动、需自行猜测、需自行翻译英文 |
| **P3（轻微）** | 11 | 文案、观感、演示数据污染 |

## 1. 系统性问题（跨页根因，修一处等于修一片）

这一节是本报告最重要的部分。28 个页面里的大量缺陷不是各自独立的 bug，而是**6 个组件级/工程级根因**在不同页面的重复投影。

### 根因 A｜表格组件缺少列宽策略 → 列塌陷、文字重叠、竖排单字

**受影响页面（8 个）**：服务请求详情、工单类型、工单管理、用户管理、权限管理、项目管理、审计日志、通知中心。

具体表现各不相同，但病根同一个——表格没有设置合理的 `min-width` / `table-layout` / 列宽分配规则，窄视口下列宽被压缩到极限：

| 页面 | 塌陷表现 |
|---|---|
| 服务请求详情 | 首列被压成每行 1 字竖排：「成 本 中 心」「数 据 分 类」「需 要 公 网 IP」 |
| 用户管理 | 用户名列竖排 `de/mo./mfg/.sec/ad/min`；部门列「信 息 技 术 部」竖排；操作列被挤出视口 |
| 工单类型 | 「名称」与「编码」两列文字重叠：`general_incident` 直接压在「通用事件」上，整行不可读 |
| 工单管理 | 「优先级」表头被裁成「优先」，与「操作」列挤压重叠 |
| 项目管理 | 健康度/进度/负责人/归属与计划 4 列被推出视口；操作列「工作台/编辑/激活/取消」文字重叠 |
| 权限管理 | 「选择角色：」标签竖排成「选/择/角/色/：」 |
| 审计日志 | 状态码、IP 两列被挤出视口——安全审计最关心的字段要横向滚动才看得到 |
| 通知中心 | 徽标数字被拆成两个节点渲染 |

**建议**：统一表格组件规范——固定列设 `width`，弹性列设 `min-width`（建议正文列 ≥ 120px），文本列允许 `word-break: break-word` 但禁止单字宽度，操作列 `sticky: right`。这是**投入产出比最高的一项修复**。

### 根因 B｜枚举值未做本地化映射 → 中英混杂、原始状态码直出

**受影响页面（7 个）**：服务请求详情/列表、工单类型、工单统计、工单管理、配置项列表、审计日志。

- 状态直出大写枚举：`SUBMITTED`（服务请求详情）
- 状态直出小写枚举：`submitted` / `cancelled`（服务请求列表）、`new` → `in_progress`（通知内容）
- 优先级直出：`medium` / `high` / `critical` / `low`（工单类型、工单统计图例）
- 工单状态图例全英文：`cancelled/closed/in_progress/new/open/pending/resolved`（工单统计）
- CI 类型直出：`application` / `database` / `network` / `server` / `storage`（配置项列表）
- 审批环节直出英文角色码：`MANAGER` / `IT` / `SECURITY`（服务请求详情）
- 审计日志「操作」列 `view`/`search`、「资源」列 `system-configs`/`roles`/`permissions`、「路径」列 `/api/v1/system-configs/status`

**关键矛盾**：「我的请求」页显示中文状态（已提交/已取消），「服务请求」页同一 N 条数据显示 `submitted`/`cancelled`——**同一个系统里两套映射**。

**建议**：建立统一的枚举字典层（status / priority / ci_type / role / operation），前端禁止直出枚举值。审计日志面向合规人员，应把 `view` 映射为「查看」、`/api/v1/system-configs/status` 映射为「查询系统配置状态」，原始值折叠到详情。

### 根因 C｜原始 ID / 技术编码未解析为人类可读名称

| 页面 | 表现 |
|---|---|
| 工单管理 | 处理人列显示「用户 #6」「用户 #3」「用户 #5」 |
| 服务请求详情 | 服务名称显示「服务 #10」 |
| 工作流管理 | 流程名混入 `service_request_flow_cn`、`scheduled_inspection_flow`、`problem_management_flow_cn`、`incident_emergency_flow_v1.1` |
| 配置项列表 | 资产名混入 `MES-APP-01`、`SW-CORE-01`、`BACKUP-STORAGE-01` |
| 流程设计器 | 默认流程名 `Process_1` |

**建议**：后端返回时附带 `display_name`，前端禁止裸 ID 渲染；技术编码作为副标题或 tooltip 保留。

### 根因 D｜页面统计口径与列表取数逻辑不一致 → 同页数字对立

这是最伤客户信任的一类问题，**同一屏里两个数字直接矛盾**：

| 页面 | 矛盾点 |
|---|---|
| **工单管理** | tab「工单列表 (26)」+ 顶部「总工单 26」，而列表底部「第 1-13 条，共 13 条」，且只有 1 页、上一页/下一页均 disabled |
| **工作流管理** | 四张 KPI 大字全为 `0`（工作流总数 0 / 运行中实例 0 / 已完成 0 / 平均执行时间 0分钟），子文案「活跃 0｜草稿 0｜停用 0」，但下方表格「共 18 / 18 个工作流」且逐行列出 10 条「已激活」 |
| **SLA 监控** | 顶部四卡「SLA总数 7 / 启用中 7/7 / 违规总数 29 / 未解决违规 29」，正下方大屏「活跃告警 0 / 未解决违规 0 条 · 告警规则 0 条」「SLA告警列表 0 明细 0 条」 |
| **工单统计** | 解决率 3.8%，但 SLA 达标率 0%、平均响应/解决时间 0.0 小时并列 |
| **通知中心** | 「共 47 条通知，未读 46 条」，tab 徽标 46，顶栏铃铛 46，已读 tab 无数字 |
| **服务请求列表** | 顶部统计「待审批 1」vs 标签页「待审批 (4)」 |

**建议**：统计卡与列表必须走同一个 count 查询；列表总数取 `total` 而非当前页长度；分页器状态与 total 联动。

### 根因 E｜图标按钮缺可访问名称 → 空白按钮、无人能懂的图标

| 页面 | 表现 |
|---|---|
| 问题管理 | 操作列按钮无文字标签（同系统「变更管理」有标签，不一致） |
| 知识库 | 操作列两个空 button（无 aria-label、无 tooltip） |
| 角色管理 | 操作列两个空 button（编辑/删除） |
| AI 评估与审计 | 「评估总览」标题右侧纯图标按钮，用途不明 |
| 流程设计器 | 14 个纯图标画布工具，全部只有英文 aria-label |

**建议**：所有图标按钮必须有 `aria-label` + tooltip；高危操作（删除/清空）必须二次确认。

### 根因 F｜成熟度标识（Pilot）滥用且逻辑倒挂

全站共有 10 处菜单项带红色「Pilot」标记：服务请求、问题管理、已知错误、知识库、新建文章、AI 助手、AI 评估与审计、AI 审批、Bot 运行看板等。

**三个问题**：
1. **标记太多等于没有标记**——10 个主菜单项带 Pilot，客户看到会认为「整个系统都是试用品」。
2. **逻辑倒挂**——「AI 创建工单」**没有** Pilot 标记（暗示可正式使用），但它配套的治理能力「AI 评估与审计」**有** Pilot 标记。即：能用的功能没护栏，护栏本身还在试点。而实测 AI 创建工单恰恰是不可用的（P1-11）。
3. **没有解释**——鼠标悬停在「Pilot」上没有任何说明「Pilot 意味着什么、能否用于生产、有无 SLA 承诺」。

**建议**：Pilot 只标注真正受控试点的功能；每个 Pilot 必须配 tooltip 说明边界；参考 CMDB 页的做法（见 §4 正面案例）——**明确写出「完成 X/Y/Z 前不在正式入口展示」，这是正确示范**。

## 2. 分模块逐页问题清单

### 2.1 服务台域

#### P1-01｜服务请求审批区视觉不渲染（最严重）

- **页面**：服务请求详情 `/service-requests/<id>`（REQ-00011）
- **现象**：DOM 快照中明确存在「审批流程 / 审批操作 / 通过 / 拒绝」节点，但页面视觉上完全不渲染——表单数据区块结束后直接跳到页脚。两次点击「通过」（uid 7166）均无弹窗、无 toast、无状态变化。
- **用户影响**：客户管理员收到待审批通知，点进去看不到任何审批入口，**审批链路彻底卡死**。第一轮未覆盖审批视角，本轮首次暴露。
- **建议**：这是 P0 级业务阻塞，需立即排查审批组件的条件渲染逻辑（是否依赖了未加载的角色/权限上下文）。

#### P1-02｜服务请求详情页大量内部值外露

- 状态显示大写 `SUBMITTED`
- 服务名称显示「服务 #10」
- 「表单数据」整段输出原始 JSON（含 `requesterEmail` 等内部字段名）
- 审批环节显示 `MANAGER` / `IT` / `SECURITY` 英文角色码

#### P1-03｜服务请求详情表格列宽塌陷

首列每行 1 字竖排，页面出现横向滚动条（见根因 A）。

#### P2-01｜「我的请求」列表把富文本原样输出

申请理由列直接显示 `<p>因远程办公需要…</p>` 原始 HTML 标签，未做 HTML 转义渲染。

#### P2-02｜服务请求列表状态未本地化

显示 `submitted` / `cancelled`，与「我的请求」页中文状态不一致（见根因 B）。

#### P2-03｜同一页出现两组重复嵌套的标签页

「我的 / 待审批」标签组重复渲染两次，且顶部统计「待审批 1」与标签页「待审批 (4)」数字矛盾。

#### ✅ 正面：服务申请表单

必填校验有效（标题、申请理由、合规承诺勾选）；提交后成功生成 REQ-00011 并明确提示「已提交，等待审批」；生成规范单号（REQ-00011），可追溯。

### 2.11 AI 域

#### P1-15｜AI 创建工单整条链路不可用（实测）

**实测步骤**：
1. 输入：「帮我申请一台 ThinkPad 笔记本，用于 Java 开发，预计下周入职使用」
2. 点击「发送」
3. AI 返回：判定为「**硬件故障（中）**」，推导依据「『笔记本』→ 硬件故障」
4. 点击「确认」
5. 页面顶部弹出红色 toast：「**请求失败，请稍后重试**」，表单未生成，流程中断

**两个独立缺陷**：

- **缺陷 1 意图分类错误**：用户需求本质是「**新申请设备**」（服务申请/采购），AI 判成「设备坏了报修」（硬件故障）。若用户直接确认，会建出错误类型的工单、走错误流程、套用错误的 SLA——**错误分类比不分类更危险**，因为用户默认 AI 是对的。
- **缺陷 2 提交接口失败**：即使分类正确，点确认也拿不到表单。整条链路当前只是 UI 演示。

#### P2-35｜AI 创建工单输入区高度塌陷

占位文案「例如：帮我申请一台 ThinkPad 笔记本，用于 Java 开发...」与右侧「发送」按钮文字在同一行严重重叠，「发送」二字被裁掉一半，输入区仅约 40px 高。

#### P2-36｜AI 评估与审计控制台零数据

- 「AI 审计日志（近 90 天，共 0 条）」
- 「工具调用审计」暂无数据
- 「评估总览（近 30 天）」整块空态

**关键矛盾**：我刚刚实测调用过 AI 创建工单（产生了意图分类结果与失败请求），但此处仍为 0 条。**AI 调用未落审计**。而空态文案写「AI 功能使用后会自动产生评估数据」——与实际行为矛盾。

**影响**：AI 决策不可追溯。对于把 AI 引入工单分类的 ITSM 系统，这是合规级缺陷。

#### P2-37｜AI 治理与 AI 功能上线顺序倒挂

「AI 创建工单」无 Pilot 标记（暗示可正式使用），配套的「AI 评估与审计」有 Pilot 标记。能用的功能没护栏，护栏本身还在试点。

#### P2-38｜AI 评估与审计图标按钮用途不明

「评估总览」标题右侧纯图标按钮，无文字、无 tooltip。

#### ✅ 正面：AI 创建工单交互闸门设计正确

AI 先展示「我理解成：XXX」+ 推导依据，要求用户「确认」或「修改」后才生成表单，并明示「不会自动提交，提交前你可核对/修改」。**这个闸门设计是对的**——即使分类错了（本次确实错了），用户也有机会纠正。问题在于分类准不准，而非闸门本身。

#### ✅ 正面：AI 创建工单两段式「先自助，再建单」

先查知识库，命中则免建单；未命中再建。空输入时「查询知识库」按钮正确 disabled。

#### ✅ 正面：AI 评估与审计表结构设计专业

审计表列（时间/场景/输入引用/模型/策略版本/可信度/采纳/操作），工具审计含「风险/状态/耗时/错误码/轨迹」——**字段设计符合 AI 治理最佳实践，只是没数据**。双维度筛选与「近 30 天/近 90 天」口径明示。

## 4. 正面案例（建议作为全站标杆推广）

第二轮审查不只有问题。以下 5 处做法明显优于其他页面，**建议提炼为设计规范**：

### ① CMDB 首页 —— 成熟度与边界披露的标杆

- 四项能力卡统一标注「**GA 候选**」成熟度徽标，用户可预判稳定性
- 主动披露：「云资源自动发现和自动对账仍处于受控试点，**完成真实连接、任务重试、审计和生产验收前不在正式入口展示**」
- 显示「数据刷新时间」，数据新鲜度可见

**这是全站唯一一个把「我们做了什么、没做什么、为什么」讲清楚的页面。** 建议把这段措辞复制到所有 Pilot 功能的入口。

### ② SLA 监控空态 —— 空态归因的标杆

「窗口内没有同时具备响应截止时间和首次响应时间的工单，暂无响应达成率样本」

不是「暂无数据」，而是**明确说出缺什么样本、为什么缺**。

### ③ 工单统计底部声明 —— 空值与零值的区分

「后端当前未提供类型分布与处理时长明细，相关指标暂为空/0，**不区分于真实零值**」

主动告知用户「这个 0 不是真的 0」。这是数据诚实的正确做法。
