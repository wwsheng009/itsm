## 一、本轮五条最高优先级结论

### 结论 1｜组织与审批基础数据全链为空，工单路由在人物层面完全断裂（P0）

这是本轮最重要的发现，且不是单页缺陷，而是一条链上**五个环节同时为空**：

| 环节 | 页面 | 实测状态 |
|---|---|---|
| 部门 | /admin/departments | **加载失败**，指标显示 0 / 0 |
| 审批组 | /admin/groups | 6 个组存在，但**成员数全部 = 0** |
| CAB 委员会 | /admin/cab | CAB、ECAB **成员均 0 人** |
| 工单分类 | /admin/tickets/categories | **0 条分类** |
| 派单规则 | /admin/tickets/assignment-rules | **0 条规则** |

同时，系统内**已存在真实业务数据**：6 个带角色的用户、22 个角色、47 条通知，以及至少 20+ 个真实工单号（TKT-202610-000062 ~ 000066 等）。

**推论（标注为推论）**：工单在持续产生，但审批组无人、CAB 无人、分类为空、派单规则为空。这解释了为什么 47 条通知里大量是「状态从 `new` 变更为 `in_progress`」「从 `open` 变更为 `in_progress`」这类**不需要任何审批人、不需要任何分类路由**的状态机自动流转，而几乎看不到审批类通知。

**影响**：任何走过 L1/L2/L3 审批、走过 CAB 评审、依赖分类派单的流程，在当前数据状态下都无法路由到具体的人。这不是"功能没做"，而是"功能做了但没有可用的人"。

**建议**：这是上线阻断项。上线前必须有组织架构与审批人的开通检查清单，并在组管理/CAB 页面对"成员为 0 但被流程引用"给出显式警示。

### 结论 2｜部门管理把"加载失败"渲染成了"没有数据"（P0）

/admin/departments 页面同时出现三个互相矛盾的信号：

- 顶部红色 toast：**「加载部门数据失败」**
- 面包屑右侧常驻红色提示：**「加载部门数据失败」**
- 指标卡：**「部门总数 0」「活跃部门 0」**
- 表格：**「暂无部门」**（图标 alt「暂无数据」）

**错误态与空态共存**，用户看到 0 和"暂无"会判断为"业务上不需要建部门"，而实际是接口失败。更严重的是，加载失败时指标卡的 `0` 是**默认初值冒充真实值**——失败必须让指标卡显示"—"或隐藏，不能用 0 填充。

同一页「新建部门」按钮在失败态下依然可点（顶部一处 + 空态内一处），点进去大概率再次失败。

### 结论 3｜权限配置与实际可见性直接冲突，且同一角色两处权限数相差 52 个（P0）

在 /admin/permissions 选择"系统管理员"后实测：

| 项目 | 实测值 |
|---|---|
| 功能模块 | 21 / 23（91.3% ✓ 可复算） |
| 操作权限 | **67 / 253**（26.5% ✓ 可复算） |
| 「系统管理」模块 | 总开关 **关闭**，11 个子权限全部 `disabled` |
| 「用户组管理」模块 | 总开关 **关闭**，子权限全部 `disabled` |

但对照 /admin/roles 页面，同一"系统管理员"的「权限数量」显示为 **119**。**67 与 119 相差 52 个权限**，两个页面必有一处错误。而 67 是通过逐模块 switch 计数得出的可核数字，119 无法核验。

更矛盾的是：**「系统管理」模块权限为关闭，但当前登录账号正在正常使用 /admin 下全部系统管理菜单**（本报告访问的 12 个页面全部位于 /admin）。权限配置与实际可见性之间存在直接冲突，与第五轮发现的「权限导航泄漏」同源——**菜单可见性不受权限配置约束**。

### 结论 4｜侧边栏「自动化规则」两个同名入口，指向两个完全不同的功能（P1）

| 侧边栏位置 | 实际 URL | 实际页面 | 面包屑域 |
|---|---|---|---|
| 管理功能·工作流组下 | `/workflow/automation` | H1「工作流自动化」 | 首页/工作流/自动化规则 |
| 系统管理·工单管理组下 | `/admin/tickets/automation-rules` | H3「工单自动化规则」 | 首页/系统管理/工单管理 |

两个菜单项**文字完全相同**，无任何区分后缀，必须点进去才知道不是同一个功能。而两者业务定位差异极大（前者是 BPMN 流程外的自动分配/路由/升级规则，后者是工单字段级条件触发）。

讽刺的是，两者的完备度正好相反：
- `/workflow/automation`：4 个 KPI 全 0（自动分配规则 0 / 智能路由规则 0 / 自动升级规则 0 / 活跃规则 0），3 个 tab 全空，是**空壳页**
- `/admin/tickets/automation-rules`：页面极简、0 条规则，但 alert 文案是**全部 6 轮里写得最好的一处**（见结论 5）

建议直接改名为「工作流自动化」与「工单自动化规则」，与各自页面标题一致。

### 结论 5｜系统配置四个页签的字段状态三档分化，可精确定位为字段级映射缺陷（P0/P1）

这是本轮方法上最有价值的一处证据。同一页面、同一保存接口，四个页签的字段呈现三种状态：

| 页签 | 有值字段 | 空字段 |
|---|---|---|
| 通用设置 | **无** | 系统名称、系统URL、时区、语言、日期格式、时间格式（**6 项全空**，均带必填星号） |
| 安全设置 | 密码最大长度 = **128** | 密码最小长度、登录失败次数限制、账户锁定时间（**3 项必填空**） |
| 邮件设置 | SMTP服务器 = `itsm-smtp-mock-a`、端口 = **2525**、密码 = **已设置**、发件人 = `ops-a@tenant-a.example` | SMTP用户名、系统通知模板 |
| AI 配置 | 有内容（Bot 能力 / MCP 开关） | 见下 |

**推理**：若读取接口整体失败 → 应全部为空；若配置从未保存 → 也应全部为空。现在是**一部分有值、一部分为空**，因此可以排除环境问题与"从未初始化"，指向**字段名映射或序列化缺陷**（部分字段读到，部分字段读不到）。

这个结论比"部门管理整体加载失败"更可定位，因为它把排查范围从"整个接口"缩小到了"具体字段"。

配套的运行时指标问题同样荒谬：系统运行时间 = **未知**、Goroutine 数 = **0**、CPU 核心数 = **0**、内存使用率 = **0%**。**一个正在渲染页面的系统不可能只有 0 个 CPU 核心、0 个 Goroutine。** 四个运行时指标全部失效。

## 三、系统性根因（跨页复现）

### 根因 A｜错误态与空态不互斥，失败被渲染成 0

- 部门管理：加载失败 + 0 指标 + 暂无部门同时出现
- 系统配置：运行时指标 0/未知，系统却在正常服务
- 权限配置：未选角色时指标全 0（此处合理，是标准空态）

**共性**：系统在多处把"取不到数据"与"数据为 0"渲染成同一种视觉结果。**修复原则**：错误态、空态、真实 0 值必须是三种不同呈现；失败时数值应显示「—」并给出重试入口。

### 根因 B｜枚举值与 code 未经本地化，直接透出

本轮出现频次（累计第 12 次）：服务方角色 `msp_specialist`/`msp_tech`、通知正文 `new`/`in_progress`/`open`、组描述引用 `l1_support`/`l2_support`/`l3_expert`/`ops_manager`/`dept_manager`/`change_manager`（且这 6 个角色在角色表中不存在）。

### 根因 C｜a11y 名被 children 拼接污染

### 根因 D｜页面标题层级混乱
