### ① 有一个 P1 结论需要下调（第二轮 P1-01）

第二轮判定「服务请求审批链路卡死」。本轮在**「待我审批-目录」页实测点击「批准」，成功返回绿色提示「审批成功」**。

### ② 补上了审批不推进的最后一环证据（新 P1）


**建议把这三条作为一个缺陷簇统一排期**，而不是三个独立 bug 分别修。

## 1. 本轮新增问题清单

### 1.1 AI 域（四页全审）

#### P1-16｜Bot 运行看板：文案模板占位符未替换，字面量直出

这是本轮视觉上最刺眼的问题。页面上多处数字位置显示的是**未经插值的 i18n 占位符**：

| 位置 | 实际显示 | 应为 |
|---|---|---|
| 时间范围标签 | `最近 {7} 天` | 最近 7 天 |
| 运行成功率 · 副文案 | `完成 {0} / 失败 {0} / 进行中 {0}` | 完成 25 / 失败 1 / 进行中 0 |
| 确认通过率 · 副文案 | `通过 {0} / 拒绝 {0} / 过期 {0}` | 通过 N / 拒绝 N / 过期 N |
| 回读失败率 · 副文案 | `通过 {0} / 失败 {0}` | 通过 N / 失败 N |
| 工具错误率 · 副文案 | `调用 {0} / 错误 {0}` | 调用 N / 错误 N |

**根因判定**：i18n 插值调用方式错误——占位符用了 `{0}` 这种索引式写法，但传参方式与之不匹配（React/i18next 默认用 `{{0}}` 或命名参数），导致模板原样输出。

**为什么这比「显示 0」更严重**：显示 0 至少是「数字不好看」，显示 `{0}` 是「这段功能根本没跑通」。客户第一眼就会认为系统没做完。

#### P2-39｜Bot 运行看板：数值被拆成两个节点渲染

「平均步数/运行」显示为 `0` + `.00`，是两个独立 DOM 节点拼接。与第二轮通知徽标「4」+「6」叠成 46 是同一类渲染问题——数值格式化层把整数部分与小数部分分开输出。

#### P2-40｜Bot 运行看板：时间维度单一

时间范围下拉只有「最近 7 天」一个可选项，无 30 天/自定义。Bot 运行趋势无法跨周期对比。

#### P2-41｜Bot 运行看板：两张分解表空态文案完全相同

「按入口分解」与「按 Bot 分解」两表空态均为「窗口内暂无数据」，未区分维度。

#### P2-42｜AI 审批：表头被截断

「权限校验」列头被裁成「权限校」，状态/创建时间/操作三列被推出视口。

#### P2-43｜AI 审批：两套空态语义不同却不作区分

- 「窗口内没有符合条件的运行」（时间窗口导致无数据）
- 「当前状态下列表为空」（筛选条件导致无数据）

这两种「空」的原因完全不同，用户无法判断是「从来没发生过」还是「被我筛掉了」。

#### P2-44｜AI 审批：零数据导致核心承诺无法验证

页面承诺「只读任务与写动作闸门；回滚会冻结该运行全部待审批」——这是 AI 安全的关键护栏。但运行监督与审批队列都是 0 条，**无法验证闸门是否真的生效**。

#### ✅ AI 域正面：三处值得保留的设计

1. **Bot 运行看板主动披露代理口径**：「token 计量尚未接线（B1-02 遗留）：成本维度以步数/工具调用数/时延为代理」，并带内部缺陷编号 `B1-02`，可追溯。**这是全站最好的口径诚实案例之一。**
2. **Bot 指标设计正交**：运行成功率 / 确认通过率 / 回读失败率 / 工具错误率四个维度互不重叠，且「成本与规模」独立分区并二次标注「成本代理口径」徽标。
3. **AI 审批的连带影响披露**：「回滚会冻结该运行全部待审批」——一句话说清危险操作波及范围，值得推广到所有高危操作。

### 1.2 审批与流程执行层

#### P1-17｜流程实例：25/27 长期「运行中」不结束

**实测数据**：

| 指标 | 值 |
|---|---|
| 总实例 | 27 |
| 运行中 | 25 |
| 已完成 | 2 |
| 已暂停 | 0 |

- 最早的运行中实例启动于 **2026/10/16 21:35**，至审查日（10/28）**已 12 天**，结束时间仍为 `-`
- 另一条运行中实例启动于 **2026/10/19 14:10**，已 9 天
- 唯一正常的已完成实例：启动 10/17 09:44:23，结束 09:44:26——**耗时 3 秒**

**判断**：需要人工审批的流程全部永久挂起，只有全自动流程能走完。这与「审批组成员全为 0」完全吻合。

**用户影响**：申请人看到「已提交，等待审批」后再无下文；管理员看到 25 条「运行中」却不知卡在哪一节点（页面无当前节点字段）。

#### P1-18｜流程实例：「业务键」列与「流程 Key」列取值完全相同

每行的「流程 Key」与「业务键」都是同一个值：

| 流程 Key | 业务键 |
|---|---|
| `service_request_flow` | `service_request_flow` |
| `ticket_general_flow` | `ticket_general_flow` |
| `change_normal_flow` | `change_normal_flow` |

**业务键（Business Key）本应指向具体业务单据**（如 `REQ-00011`、`TKT-202610-000062`），用于把流程实例与业务对象关联。现在被回填成流程定义 Key，导致：
- 用户无法从实例列表定位到具体是哪一单
- 无法反查「REQ-00011 走到哪一步了」

#### P2-45｜流程实例：实例 ID 外露雪花号

`PI-service_request_flow-1793153403639481564` —— 21 位雪花 ID 直接作为主键展示，无法口述、抄录、在搜索框输入。

#### P2-46｜流程实例：实例 ID 列宽不足，折成三行

`PI-` / `service_request_flow-` / `1793153403639481564` 三行堆叠，行高被撑大。

#### P2-47｜流程实例：承诺的「持续时长」未实现

页面描述明确写：「查看流程实例的运行状态、**起止时间和持续时长**，支持按状态和流程筛选。」

但表格只有「启动时间」「结束时间」两列，**没有持续时长列**，也没有「已运行 12 天」这类派生计算。功能描述与实现不符。

#### P3-13｜流程实例：暂停/终止无二次确认

「终止」是不可逆高危操作，与「详情」「暂停」并排，未点击验证是否有确认弹窗。

#### ✅ 流程实例正面：KPI 与列表口径一致

四张卡（27 / 25 / 2 / 0）与列表数据完全自洽，**没有出现第二轮里「工作流管理 KPI 0 vs 列表 18」那类矛盾**。说明同一团队在别的页面做对了，是取数实现不一致而非能力问题。

#### ✅ 流程实例正面：版本边界披露清晰

页面顶部 banner：「**本版本** 支持实例列表、状态操作（暂停/恢复/终止）和详情查看。任务列表与会签视图将在后续版本补充。」

## 3. 三轮累计的核心结论

### 3.1 缺陷聚类：不是一个一个 bug，是四条断掉的链路

把三轮 90 项问题按因果重新组织，会看到四个**断点**：

#### 断点一：审批链路（最严重）

```
审批组 0 人 ─┐
CAB 成员 0 人 ─┼→ 流程实例 25/27 永久运行中 ─→ SLA 违规 29 条永不解决
详情页不渲染 ─┘
```

修这一条需要四个动作：给审批组灌人、给 CAB 灌人、修详情页审批区块、修 SLA 取数。**任何一个不修，链路仍然断。**

#### 断点二：AI 域（全站最不成熟，却唯一没标 Pilot）

```
AI 建单：分类错 + 接口失败
AI 审计：0 条（调用不落审计）
AI 审批：0 条
Bot 看板：占位符外露
```

四个页面全不可用，但「AI 创建工单」**没有 Pilot 标记**。这是上市节奏问题，不是技术问题。

#### 断点三：数据可信度（最伤客户信任）

三轮共发现 **8 处同页数字对立**：

| 页面 | 矛盾 |
|---|---|
| 工单管理 | 26 vs 13 |
| 工作流管理 | 0 vs 18 |
| SLA 监控 | 违规 29 vs 0 |
| 通知中心 | 47 vs 46 |
| 服务请求 | 待审批 1 vs 4 |
| 仪表盘 | ↑0.0% vs +100.0% |
| 流程实例 | 27(总) 但已完成仅 2、25 恒运行 |
| 权限管理 | 模板写入 165 项 vs 权限字典未初始化 |

**注意一个正面反例**：流程实例页的 KPI（27/25/2/0）与列表完全一致。说明**能力没问题，是各页面取数实现不统一**。

#### 断点四：本地化与格式化（覆盖面最广）

三轮累计：
- 英文枚举外露：**11 个页面**（status/priority/ci_type/role/operation/edge_type）
- 原始 ID 未解析：**7 个页面**（用户 #N、服务 #N、裸数字 ID、雪花 ID）
- 时间格式不统一：ISO 原始串 vs `YYYY-MM-DD HH:mm` 并存
- i18n 占位符未插值：Bot 看板

**这一条是投入产出比最高的**——建一套字典层 + 一套格式化工具函数，能一次消掉约 20 项问题。

### 3.2 与工作流/流程设计器页的对比说明

同一团队在**流程实例页**（KPI 自洽、版本边界披露、时间格式正确、按钮带文字）和**工作流管理页**（KPI 全 0 vs 列表 18、流程名混入 `service_request_flow_cn`、分类中英混杂）表现出完全不同的质量。

**结论**：这不是「团队能力不足」，而是**缺少统一的前端规范与代码复用**。流程实例页是后做的，做对了；工作流管理页是先做的，遗留了问题。建议做一次横向对齐，把流程实例页的实现作为参考。
