## 0. 结论先行

前四轮的主线是「指标不自洽」（Round2-3）与「跨页数据链断裂」（Round4）。本轮把视角下沉一层，转向**页面与它宣称的功能是否名副其实**，结果指向一个更基础的问题：

> **很多页面已经"建好了壳"，但壳里面是空的，或者装的不是它标称的东西。**

四个典型：

| 页面 | 叫这个名字 | 实际是什么 |
|---|---|---|
| 资源中心 | 资源池/资产视图 | **Agent Skills 技能包下载中心**（面向开发者） |
| 工具目录 | 内置 + MCP 外部工具 | **25 个全是内置，0 个 MCP** |
| CMDB 类型 | CI 类型（含属性模型） | **8 个类型属性模板全部「未配置」** |
| 客户管理 | 可访问的菜单 | **点击即 403，本角色无权** |

同时本轮发现一个**可被跨页反证的 P0 缺陷**：操作日志页 20 行「操作人」全为空，而审计日志页同一时刻同一用户正常显示「陈志远（制造-管理员）」。这证明它不是数据缺失，而是字段映射写错了——修复成本远低于表面判断。

### 本轮最高优先级四条

| # | 结论 | 影响 |
|---|---|---|
| **A** | 操作日志「操作人」列 20 行全空，且已被审计日志页反证为字段映射 bug | 审计追溯能力归零，**P0** |

## 1. 核心发现 A【P0】：操作日志「操作人」全空，且能被跨页反证

### A-1 实测情况

`/workflow/audit`（H1「BPMN审计日志」）表格共 20 行，三个关键列全空：

| 列 | 20 行实测 |
|---|---|
| **操作人** | **全部为空** |
| 受理人 | 全部为空 |
| 备注 | 全部为空 |

**审计日志的核心价值就是回答"谁在什么时候做了什么"。操作人一列为空，这个页面就失去了审计功能。**

### A-2 关键反证：数据是存在的，只是没被显示

`/audit-logs`（H4「审计日志」）在同一浏览器会话、同一账号、同一时刻，20 行「用户」列**全部正常显示「陈志远（制造-管理员）」**。

> 同一用户、同一会话、同一时刻，一个页面能显示操作人，另一个不能。
> → **不是数据缺失，而是 BPMN 审计页的「操作人」字段查询或映射写错了。**

这条反证把问题从「整套审计数据没采集」缩小到「一个字段没 join 上」，修复成本大幅降低，应作为本轮 P0 第一优先。

### A-3【P1】「用户ID」筛选用 spinbutton，且 max=0

- 该筛选控件在 a11y 树中是 `spinbutton`（数字微调框），`valuemin=0`、**`valuemax=0`**。
- max=0 意味着**永远无法输入任何有效值**。
- 更严重的是：实际流程实例 ID 是 19 位长整型（如 `1793153403639481564`），spinbutton 本身也装不下。
- 表单控件类型误用，该筛选项完全不可用。

### A-4【P1】侧边栏同时有「操作日志」与「审计日志」，且确实不是同一功能

实测确认两者**不是重复**，但命名让人分不清：

| 菜单 | URL | 内容 | 规模 |
|---|---|---|---|
| 操作日志 | `/workflow/audit` | BPMN 流程节点事件 | 37 条 / 2 页 |
| 审计日志 | `/audit-logs` | HTTP API 调用审计 | 711 条 / 36 页 |

前者是「业务流程走了哪些节点」，后者是「谁调了哪个接口」。数据源、粒度、用途完全不同，却分别叫「操作日志」与「审计日志」——**用户无法从名称区分该进哪个**。建议改名为「流程事件日志」与「API 审计日志」。

### A-5【P2】操作日志页其他问题

- 操作类型英文枚举 `started` / `completed`（根因 B 第 8 次）。
- 「流程定义Key」是**自由文本框无候选下拉**，而版本管理页对同一概念提供了 Key 下拉。用户必须逐字手打 `service_request_flow`。
- 同一功能三个名字：侧边栏「操作日志」+ 面包屑「工作流 / 操作日志」+ H1「BPMN审计日志」。
- 「总计 37 条」与流程实例页「总实例 27」口径未说明。37 是节点级事件数（如 `PI-change_normal_flow` 单实例产生 6 条：流程开始/CAB审批/变更排期/变更实施/变更验证/关闭变更），但页面未说明「1 条 = 1 个节点事件」而非「1 个实例」。
- 无导出功能，只有「刷新」。
- H1「BPMN审计日志」被顶栏压住，截图中几乎不可见（根因 E 第 5 次）。
- 顶部通知数「46」在 a11y 树中被拆成「4」+「6」两个文本节点（无障碍拆分第 4 次）。

### A-6 ✅ 操作日志页做对的地方

- **时间格式已本地化** `2026/10/28 10:24:58`（对比 SLA 定义页的 ISO 原样 `2026-10-13T08:14:54.072365Z`）——说明系统**有**格式化能力，只是没统一。
- 操作类型色彩区分（completed=绿、started=蓝）。
- 操作列提供「查看」+「时间线」双入口，可从事件下钻到实例轨迹。
- 「活动名称」用中文业务语义（流程开始/请求受理/变更排期/CAB审批），比纯状态码可读。
- 分页正确：总计 37 条 / 20 条每页 / 2 页，第 1 页「上一页」正确禁用。

## 2. 核心发现 B【P1】：权限导航泄漏 —— 客户管理点击即 403

### B-1 实测

- 侧边栏（`uid=802`）对当前角色展示「客户管理」菜单项，且带有一个青色地球图标。
- 点击后**直接跳转 `/403`**，页面显示「抱歉，您没有访问该页面的权限。」

**侧边栏作为导航入口，对所有菜单项一视同仁，未按权限过滤或置灰。** 用户点了才知道无权访问。这是一次导航级权限泄漏：每点一次都是一次无效往返。

正确做法二选一：无权菜单**隐藏**，或**置灰 + tooltip 说明所需权限码**。

### B-2【P2】403 页自身的问题

- **面包屑语义错乱**：显示「首页 / 详情 #403」，把 HTTP 错误码 403 当作「详情 ID #403」渲染。用户会以为这是一个叫 #403 的详情页。
- **「返回上一页」按钮在此场景无效**：用户是从侧边栏菜单直接进来的，历史记录里没有「上一页」的业务页面可返回。
- **无「申请权限」可操作路径**：文案写「请联系管理员调整角色或权限」，但没有跳转到申请工单的入口，也不告诉用户缺哪个权限码，只让用户自己去问。

### B-3 ✅ 403 页做对的地方

- 三段式表达完整：Unauthorized 插画 + 大字 `403` + 中文原因说明，用户一眼知道发生了什么。
- 提供「返回仪表盘」兜底出口，不会走进死胡同。

## 4. 核心发现 D【P1】：两个平台级能力都是空壳

### D-1 CMDB 类型（`/admin/cmdb-types`）

**【P1】8 个 CI 类型「属性模板」全部「未配置」**

- 属性模板是 CI 类型的核心定义——没有属性模板，就无法记录任何资产属性（IP、CPU、厂商、序列号……）。
- 8 个类型（server/database/network/storage/app/middleware/cloud_vm/kubernetes）全部「未配置」。
- **这与 Round4 服务目录管理页「关联CI类型」列 3 行全空互相印证**：CI 类型建了，但没有任何地方真正用上。

**其他问题**：

- 【P2】「图标」列内容与类型名称重复——kubernetes 行图标列就是 `kubernetes`，cloud 行就是 `cloud`……8 行全是与「类型名称」第二行完全相同的英文 key，**不是图标**。列名承诺「图标」，实际是重复的 code。
- 【P2】同一页面两个名字：侧边栏/面包屑「CMDB 类型」、H1「CI类型管理」、副标题「管理CMDB配置项类型」。
- 【P2】「类型名称」列严重竖排挤压——8 个类型名全部换成 2 行显示，而右侧「创建时间」「操作」列留白充足。
- 【P2】操作列 2 个按钮全部无文字无 accessible name（a11y 为裸 `button`），8 行共 **16 个无名按钮**。
- 【P2】侧边栏当前选中项渲染错乱——「CMDB 类型」文字与一枚圆形图标重叠压在一起，菜单文字被遮挡。
- 【P3】仅 8 条记录仍渲染完整分页器。

**✅ 优点**：

- 三项指标完全自证：**总类型数 8 = 激活 8 + 停用 0**，与表格 8 行一致。
- 「颜色」列除裸 hex 值外**同时渲染了对应色块预览**（绿/紫/红/靛/粉/青/橙/绿），色值与色块一致，比纯文本好得多。
- 提供「CI 类型怎么用」折叠帮助。
- 8 种类型覆盖标准 CMDB 分类，分类体系专业。

### D-2 Bot 管理与授权（`/admin/bots`）

**【P1】表格完全没有总数指标**

- 「受众」区分「内部人员」与「不限」（S3 知识自助助手对外开放），权限边界表达清楚。

## 5. 审计日志（`/audit-logs`）：表结构最专业，但横向溢出

本页作为 A-2 的反证来源已详述，此处补充其自身问题与优点。

### 【P1】「来源」列语义错误

- 该列实际显示「请求头」与「登录」两种值。
- 「请求头」不是"来源"（来源应指 web/api/cli/sdk），而是**凭证位置**；「登录」又是事件类型。
- **两个不同维度的值被塞进同一个「来源」列。**

### 【P1】表格横向溢出，路径/状态码/IP 三列在 1920 视口下不可见

- 列头共 10 列（时间/用户/操作/资源/路径/方法/来源/令牌/状态码/IP），截图在「令牌」列处被裁切，需横向滚动。
- 而「路径」与「状态码」恰恰是 API 审计最关键的定位信息。

### 【P2】其他

- 「令牌」列 20 行全为 `-`，无任何有效数据却占用列位，挤压其他关键列。
- 操作列英文枚举 `search` / `create` / `view`（根因 B 第 9 次）；资源列英文复数 code：`users` / `roles` / `service-requests` / `system-configs` / `ai` / `sla`。
- **标题层级错误**：本页标题为 **H4**「审计日志」，而其他所有页面均为 H1。
- 无导出功能——711 条 API 审计记录无法导出，取证困难。
- 筛选器 6 个中 3 个无选中值展示（「请求方式」「结果状态」「来源」），且与 3 个文本框混排无分组。
- 【P3】顶部通知数「46」视觉上正常，但 a11y 树拆成「4」+「6」，屏幕阅读器会读成"四 六"。

### ✅ 优点

- **「用户」列完整显示姓名+角色**（陈志远（制造-管理员）），比裸 ID 可读。
- 表结构专业——10 个字段覆盖完整 API 审计要素。
- 方法用色彩区分（GET=绿、POST=橙），状态码单列。
- **分页最强大**：共 711 条 / 20 条每页 / 36 页 / 支持「向后 5 页」跳转 / 跳至 N 页，第 1 页「上一页」正确禁用。
- 时间已本地化 `2026/10/28 10:26:08`。
- 查询 + 重置双按钮，筛选后可一键还原。
- 面包屑极简（首页 / 审计日志），未塞入多余层级。
